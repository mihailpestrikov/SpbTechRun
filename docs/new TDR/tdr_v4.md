# TDR: ML-система рекомендаций сопутствующих товаров

---

## 1. Summary

### Бизнес-задача

Покупатель строительных материалов при выборе основного товара часто не знает, что ещё нужно докупить, забывает сопутствующие материалы или выбирает несовместимые. Система автоматически определяет контекст покупки — к какому типу ремонтных работ относится товар — и рекомендует недостающие товары из связанных категорий. Это повышает средний чек и снижает количество «неполных» покупок, когда клиент возвращается за забытым инструментом или расходником.

### Что делаем

ML-сервис рекомендаций и Go-бэкенд для работы с данными магазина.

### Ключевые технические решения

- Семантические эмбеддинги товаров (768 измерений) через локальную модель
- Двухуровневое ранжирование: FAISS для быстрого поиска кандидатов + CatBoost для ML-ранжирования по признакам
- Сценарный подход: предопределённые наборы категорий для разных видов ремонтных работ
- Система фидбека с байесовским сглаживанием и непрерывным дообучением модели
- Дополнительная модель комплементарности категорий для cross-category рекомендаций

### Основной стек технологий

| Компонент | Технология                      |
|-----------|---------------------------------|
| Go-бэкенд (Data API) | Go 1.26, Gin                    |
| Python ML-сервис | Python, FastAPI                 |
| База данных | PostgreSQL                      |
| Векторный поиск | FAISS                           |
| ML-ранжирование | CatBoost                        |
| Генерация эмбеддингов | Ollama, изучить модели          |
| Модель комплементарности | scikit-learn LogisticRegression |

## 2. Архитектура системы

### 2.1 Целевая схема

Архитектура состоит из двух сервисов с разделением ответственности. Go-бэкенд отвечает за интеграцию с источниками данных магазина.

Python ML-сервис занимается ML-логикой: держит в памяти FAISS-индекс и обученную CatBoost-модель, выполняет весь pipeline от получения запроса до выдачи ранжированного списка рекомендаций. Для получения данных он обращается напрямую в PostgreSQL.

Разделение позволяет масштабировать и деплоить сервисы независимо, а также переписывать Go-часть (адаптер к конкретной инфраструктуре магазина) без изменений в ML-логике.

**Что убрано по сравнению с хакатоном:** Redis (кэш корзины, JWT-сессии), Elasticsearch (полнотекстовый поиск), весь фронтенд.

## 3. ML Pipeline

### 3.1 Режимы рекомендаций

Сейчас в ML-сервисе реализованы три режима рекомендаций:

- **Тип 1** — рекомендации на странице товара;
- **Тип 2а** — рекомендации для страницы конкретного сценария;
- **Тип 2б** — автоматический выбор сценария по корзине и дальнейшие рекомендации по нему.

### 3.2 Рекомендации для страницы сценария (Тип 2а)

Это основной текущий сценарий работы системы.

**Контекст:** пользователь находится на странице сценария ремонта и передаёт товары, уже добавленные в корзину.

**Вход:** `scenario_id`, `cart_product_ids`

#### Как это работает сейчас

1. **Загрузка сценария**
   - ML-сервис берёт сценарий из предопределённого набора в коде.
   - Для сценария известны группы товаров, `category_ids`, признак `is_required` и порядок `sort_order`.

2. **Анализ корзины**
   - По `cart_product_ids` загружаются товары из БД.
   - Для каждой группы сценария проверяется, есть ли в корзине хотя бы один товар из её `category_ids`.
   - Группы делятся на:
     - **completed** — уже закрыты товарами из корзины;
     - **missing** — по ним нужно строить рекомендации.

3. **Получение кандидатов для каждой незакрытой группы**
   - Выполняется SQL-запрос по `category_ids` группы.
   - Из выборки исключаются товары, уже лежащие в корзине.
   - Берётся до 100 товаров.
   - Одновременно загружаются эмбеддинги кандидатов и эмбеддинги товаров из корзины.
   - Дополнительно загружается `scenario_feedback_stats` для `scenario_id + group_name + candidate`.

4. **Скоринг кандидатов**
   - Для каждого кандидата считается формульный score

   - После расчёта score ограничивается в диапазоне `[0, 1]`.

5. **Отбор top-N**
   - Кандидаты сортируются по score.
   - Для каждой незакрытой группы возвращается top `limit_per_group` (по умолчанию 10).

6. **Расчёт прогресса**
   - Прогресс считается только по обязательным группам:

7. **Режим альтернатив**
   - Если в сценарии все обязательные группы закрыты, сервис строит блок "Альтернативы".
   - Для товаров из корзины ищутся другие товары из той же категории.
   - В текущей логике дополнительно предпочитаются товары другого производителя.

#### Что возвращает сервис

- сценарий;
- прогресс по обязательным группам;
- рекомендации по незакрытым группам;
- список уже закрытых групп с товарами из корзины;
- список всех доступных сценариев.

#### Слабые места текущей реализации

- Кандидаты берутся прямым SQL-запросом по категориям группы и сортируются не по релевантности, а по порядку выборки. Точно нужно изменить выбор первичного пула кандидатов.
- Сценарный режим не использует CatBoost. Ранкинг по формуле очень слабо.
- Сценарный режим не использует модель комплементарности категорий, хотя она есть в проекте.
- Персонализация ограничена только сходством кандидата с товарами из текущей корзины.
- Косинусное сходство плохо работает для функционально дополняющих, но семантически далёких категорий.
- Альтернативы показываются только когда закрыты все обязательные группы.

### 3.3 Авто-определение сценария по корзине (Тип 2б)

Этот режим используется, когда у пользователя есть корзина, но сценарий явно не выбран.

**Вход:** `cart_product_ids`

#### Как это работает сейчас

1. Загружаются категории всех товаров из корзины.
2. Для каждого сценария считается, сколько обязательных групп уже покрыто текущими товарами.
3. Выбирается сценарий с наибольшим прогрессом.
4. После этого сервис вызывает тот же pipeline, что и в Типе 2а.

#### Слабые места текущей реализации

- Выбор сценария основан только на покрытии обязательных групп.
- Если совпадений нет, используется сценарий по умолчанию. (лучше сделать нижнюю границу совпадения, чтобы не показывать сценарий всем)
- Не учитывается уверенность определения сценария и смешанные корзины с несколькими типами работ.

### 3.4 Рекомендации на странице товара (Тип 1)

Этот режим сильнее реализован, но для качественных рекомендаций все равно недостаточно.

**Контекст:** пользователь открыл карточку конкретного товара.

**Вход:** `product_id`, опционально `cart_product_ids`

#### Как это работает сейчас

1. Загружается товар и определяется, входит ли его категория в один из сценариев.
2. Если товар попадает в сценарий:
   - кандидаты берутся из других групп этого сценария;
   - по каждой группе выбирается до 50 товаров;
   - затем кандидаты ранжируются либо формулой, либо CatBoost-моделью, если она обучена.
3. Если товар не попадает в сценарий:
   - используется FAISS;
   - ищутся ближайшие соседи по эмбеддингам;
   - затем применяются фильтры по категориям, co-purchase и penalty за другую корневую категорию.
4. Возвращается top-20 товаров с score и `match_reasons`.

#### Слабые места текущей реализации

- Качество заметно зависит от того, найден ли сценарий для категории товара.
- Альтернативы текущему товару отдельно не реализованы.
- Для товаров вне сценариев качество в основном опирается на эмбеддинги и ограниченный набор сигналов.

### 3.5 Общие ML-компоненты, которые используются сейчас

#### Эмбеддинги товаров

- Для товаров генерируются 768-мерные эмбеддинги через Ollama.
- Эмбеддинги хранятся в PostgreSQL.
- При старте сервиса они загружаются в память.

#### FAISS

- В памяти строится `IndexFlatIP`. (в случае >1M товаров стоит заменить на индекс без точного перебора)
- FAISS используется для семантического поиска кандидатов в Типе 1.
- В сценарных рекомендациях FAISS сейчас не используется.

#### CatBoost Ranker

- В проекте есть обучаемый CatBoost Ranker.
- Он работает для парной задачи `(основной товар, кандидат)`.
- В текущем виде он применяется только для рекомендаций на странице товара.
- В сценарных рекомендациях он не используется.

#### Модель комплементарности категорий

- В проекте есть отдельная модель комплементарности категорий. Показывает, какие категории связаны друг с другом.
- Её скоры используются как признаки для товарных рекомендаций.
- В сценарном режиме эта модель сейчас не участвует в расчёте score.

## 4. Данные и обучение

### 4.1 Какие данные используются сейчас

В текущей реализации ML-сервис опирается на несколько таблиц и служебных сущностей.

| Таблица / сущность | Как используется сейчас |
|--------------------|-------------------------|
| `product_embeddings` | Эмбеддинги товаров для FAISS и расчёта similarity |
| `product_stats` | Популярность товара: просмотры, добавления в корзину, заказы |
| `copurchase_stats` | Совместные покупки для товарных рекомендаций |
| `pair_feedback_stats` | Агрегированный фидбек по парам товаров |
| `scenario_feedback_stats` | Агрегированный фидбек по сценарию и группе |
| `recommendation_events` | Логи показов и действий, но напрямую в обучении почти не участвуют |
| `SCENARIOS` в коде | Конфигурация сценариев и групп, хранится не в БД, а в Python-коде |

#### Слабые места

- Данные для сценарных рекомендаций и данные для товарных рекомендаций устроены по-разному.
- Для сценарного режима в БД мало специализированных сигналов, кроме `scenario_feedback_stats`.
- Сценарии не хранятся в БД и не управляются через данные. Нужно сделать админку и хранение сценариев.

### 4.2 Что используется для обучения и скоринга

#### Товарные рекомендации

Для Типа 1 используются:

- эмбеддинги товаров;
- co-purchase статистика;
- pair feedback;
- scenario feedback;
- product stats;
- признаки комплементарности категорий.

Для этой задачи в проекте есть полноценный feature extraction и отдельная CatBoost-модель.

#### Сценарные рекомендации

Для Типа 2 используются только:

- список групп сценария;
- категории товаров в корзине;
- эмбеддинги кандидатов и корзины;
- `scenario_feedback_stats`;
- скидки.

Отдельного обучаемого ранкера под сценарный режим сейчас нет.

#### Слабые места

- Обучение ориентировано в первую очередь на товарные рекомендации, а не на сценарные.
- Сценарный режим использует гораздо более узкий набор сигналов, чем товарный.

### 4.3 Cold start и синтетический фидбек

Для начального запуска используется скрипт `generate_synthetic_feedback.py`.

Он создаёт искусственный фидбек по товарам на основе эмбеддингов

Это нужно, чтобы CatBoost можно было обучить на пустой системе.
В проде можно заранее начать собирать фидбек.

### 4.4 Сценарии как данные

Сейчас сценарии ремонта не хранятся в БД. Они зашиты в `scenarios.py` как набор Python-объектов:

- `Scenario`;
- `ScenarioGroup`;
- словарь `CATEGORY_IDS`;
- словарь `SCENARIOS`.

В коде уже описано 5 сценариев

У каждой группы есть:

- название;
- список `category_ids`;
- признак обязательности;
- порядок отображения.

#### Слабые места

- Нужно сделать хранение и управление сценариями.

### 4.5 Как переобучается модель сейчас

Переобучение запускается через `POST /ml/train`.

#### Что делает обучение

1. Читает данные из PostgreSQL.
2. Формирует обучающую выборку для задачи `(main_product_id, candidate_id)`.
3. Позитивы берёт из:
   - `pair_feedback_stats`;
   - co-purchase из истории заказов.
4. Негативы берёт из:
   - отрицательного pair feedback;
   - hard negatives.
5. Обучает `CatBoostRanker`.
6. Сохраняет модель на диск и загружает её в память.

#### Что важно

- Группировка при обучении идёт по `main_product_id`.
- Это обучение покрывает товарные рекомендации.
- Сценарные рекомендации напрямую в этом обучении не представлены.

#### Слабые места

- Существующее переобучение не улучшает Тип 2 напрямую.
- Для сценарных рекомендаций нет отдельной обучающей выборки и отдельной модели.

### 4.6 Модель комплементарности категорий

В проекте есть отдельная модель комплементарности категорий.

#### Как она устроена сейчас

- это `LogisticRegression`;
- обучается на отдельном CSV-файле с размеченными парами категорий;
- после обучения результаты сохраняются на диск;
- при старте сервиса модель загружается в память.

#### Где она используется

- в признаках для товарных рекомендаций;
- как дополнительный сигнал при ранжировании кандидатов в Типе 1.

#### Слабые места

- Модель обучается не на live-данных магазина, а на отдельной разметке.
- В сценарных рекомендациях этот сигнал сейчас не задействован.

## 5. API ML-сервиса

ML-сервис предоставляет REST API. Эндпоинты разделены на три группы: рекомендации (получение ответов), данные (фидбек и события) и управление (обучение, статус).

При старте сервис последовательно инициализирует все компоненты перед тем как начать принимать запросы:
1. Подключение к PostgreSQL и инициализация схемы
2. Загрузка конфигурации сценариев
3. Загрузка эмбеддингов из БД и построение FAISS-индекса *(самый долгий шаг)*
4. Вычисление эмбеддингов категорий для модели комплементарности
5. Загрузка обученных моделей с диска (CatBoost + комплементарность)

## 6. Производительность и надёжность

### 6.1 Latency по шагам pipeline

| Операция | Время | Примечание |
|----------|-------|------------|
| FAISS search (k=100) | ~1ms | In-memory, IndexFlatIP, ~60k товаров |
| Feature extraction (44 признака × 100 кандидатов) | ~10ms | Batch SQL запросы |
| CatBoost predict (100 кандидатов) | ~50ms | CPU inference |
| Полный цикл рекомендаций | < 100ms | Без сетевых задержек |
| Генерация одного эмбеддинга (Ollama) | 50–200ms | Только при добавлении нового товара |

### 6.2 Масштабирование до 1M товаров

Текущая реализация работала на ~60k товаров. При переходе к 1M+ возникают два ключевых ограничения:

**FAISS IndexFlatIP при 1M товаров:**
- Потребление памяти: 1M × 768 × 4 байта ≈ **3 GB** только на индекс
- Время поиска: ~100ms (против ~1ms при 60k) — линейная зависимость от размера
- Решение: переход на `IndexIVFFlat` или `IndexHNSW` — приближённый поиск, ускорение в 50–100 раз при потере точности < 5%

**Хранение эмбеддингов в PostgreSQL:**
- 1M × 768 float ≈ 3 GB в таблице `product_embeddings`
- При загрузке в память при старте нужно передать весь объём через сеть
- Потенциальное решение: pgvector для хранения и поиска без отдельного FAISS, или предзагруженный FAISS-индекс на диске

## 7. Открытые вопросы

Этот раздел фиксирует вопросы, которые нужно прояснить в самом начале проекта. Они нужны не только для сценарных рекомендаций, но и для того, чтобы сразу заложить архитектуру под другие режимы: рекомендации в корзине, в карточке товара, на главной, в checkout и т.д.

1. **Кто владеет сценариями в бизнесе?**  
   Подходит ли решение с ручным определением сценариев и групп в них? Кто будет определять состав сценариев, обязательность групп и правила актуализации: команда e-commerce, категория, маркетинг, контент-менеджеры. В каком виде нужна админ панель для этого?

2. **Нужен ли бизнесу управляемый процесс изменения сценариев?**  
    Например: черновик, публикация, откат изменений.

3. **Сценарии должны быть жёстко предопределёнными или допускается их частичная динамика?**  
   Закладываться ли на расширение сценариев и смену категорий после публикации. Или принять, что сценарий сначала создается, проверяется, потом включается отображение.

4. **Как обрабатывать корзины, которые соответствуют нескольким сценариям сразу?**  
   Допускаем ли один основной сценарий (выбирать случайно?), несколько сценариев.

5. **Откуда приходит каталог и кто источник правды?**  
   Нужно узнать, откуда берутся товары, категории, цены, наличие, производители, акции, изображения и описания, а также как часто эти данные обновляются. Скорее всего нужно иметь свою копию бд с нужными полями и поддерживать ее событийной моделью.
6. **Есть ли доступ к истории заказов в достаточной детализации?**  
    Для co-purchase и обучения нужно знать, есть ли order items, за какой период, какого качества и можно ли их использовать регулярно.

7. **Есть ли доступ к событиям корзины и пользовательским сессиям?**  
    Для сценарных и корзинных рекомендаций важно, доступны ли add-to-cart, remove-from-cart, просмотры, переходы, session_id, user_id и снимки корзины. Или этот функционал нужно дорабатывать.

8. **Можно ли связать показ рекомендации с последующим действием?**  
    Нужно научиться понимать, что пользователь сделал после того, как ему показали конкретную рекомендацию. Добавил ли в корзину, купил ли.

9. **Как должен ML-сервис получать данные внутри recommendation-системы?**
    Либо напрямую читать общую PostgreSQL-базу recommendation-контура, либо получать данные только через Go backend/API.

10. Какой масштаб каталога?
11.  Нужно ли учитывать офлайн-магазины и различия по складам / регионам?
12.  Насколько важна explainability: нужно ли объяснять, почему товар рекомендован? 
13. Подходит ли текущий формат сценариев как набора групп категорий, или нужна более гибкая сущность?
14. Нужно ли автоопределение сценария по корзине как отдельный режим, или сценарий должен задаваться только явно переходом на страницу сценария?
15. Оставлять ли явный пользовательский feedback, или лучше делать ставку в основном на неявные сигналы?
16. Можно добавить на странице сценариев подсказки, как посчитать необходимый объем по материалам в виде "типсов"
17.  Должен ли сценарий сохраняться между заказами пользователя, например если купил часть товаров в прошлый раз, при следующем посещении закрыть часть товаров из сценария, проверил историю заказов.

## 8. Необходимые доработки

### 8.1 Доработки Go-бэкенда (Data API)

- Реализовать загрузку и регулярную синхронизацию каталога магазина в recommendation-контур: товары, категории, цены, наличие, акции, бренд, базовые характеристики.
-  Завести свою структуру для recommendation-системы для хранения необходимых данных для обучения и рекомендаций 
- Подключить историю заказов для расчёта co-purchase и последующего обучения.
- Подключить сбор событий пользовательского поведения: показ рекомендаций, клик, add-to-cart, order.
- Связать показ рекомендации с последующим действием пользователя, чтобы эти данные можно было использовать для обучения.
- Обеспечить передачу в ML-сервис актуального контекста корзины и сценария.

### 8.2 Доработки ML-сервиса

- Переделать retrieval для сценарных рекомендаций: уйти от выборки "первых товаров из SQL" к более релевантному первичному пулу кандидатов.
- Вынести сценарные рекомендации в отдельную ML-задачу, а не оставлять их на формульном скоринге.
- Добавить отдельный ранкинг для Типа 2 с учётом корзины, группы сценария и накопленного фидбека.
- Подключить в сценарный режим дополнительные сигналы: co-purchase, поведенческие данные, комплементарность категорий.
- Улучшить автоопределение сценария по корзине: учитывать смешанные корзины и вводить порог уверенности.
- Переработать логику альтернатив, чтобы они не зависели только от случая, когда обязательные группы уже закрыты.
- Сделать pipeline обновления эмбеддингов и serving-индекса при изменении каталога.
- Разделить переобучение товарного и сценарного ранкеров.

### 8.3 Инфраструктурные изменения

- Добавить событийное обновление витрины данных сервиса рекомендаций.  
- Добавить базовый мониторинг качества и технического состояния recommendation-сервиса.

### 8.4 Изменения схемы данных

- Добавить таблицы / структуры для хранения сценариев, групп сценариев и привязки категорий к группам.
- Добавить таблицы для логирования показов рекомендаций и последующих действий пользователя.
- Добавить сущности для хранения контекста сценарного запроса: сценарий, группа, корзина, позиция рекомендации.
- Подготовить таблицы / агрегаты для обучения сценарного ранкера.
- Отделить данные каталога магазина от ML-данных: эмбеддинги, co-purchase, feedback, feature-агрегаты.

### 8.5 Актуализация сценариев

- Подготовить процесс редактирования сценариев.
- Определить правила выбора сценария для смешанных корзин.
- Подготовить процесс дальнейшего сопровождения сценариев после запуска.

### 8.6 Требования к ресурсам

Для запуска одной ноды, на которой размещаются `Go backend`, `Python ML service` и периодическое обучение моделей, можно закладываться на следующую конфигурацию:

- `8 vCPU, 32 GB RAM, 200 GB SSD` - примерно минимальная конфигурация для пилота с каталогом порядка сотен тысяч товаров.
