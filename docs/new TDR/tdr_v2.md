## 1. Executive Summary

### Бизнес-задача

Покупатель строительных материалов при выборе основного товара часто не знает, что ещё нужно докупить, забывает сопутствующие материалы или выбирает несовместимые. Система автоматически определяет контекст покупки — к какому типу ремонтных работ относится товар — и рекомендует недостающие товары из связанных категорий. Это повышает средний чек и снижает количество «неполных» покупок, когда клиент возвращается за забытым инструментом или расходником.

### Что строим

ML-сервис рекомендаций и Go-бэкенд для работы с данными магазина. 
### Ключевые технические решения

- Семантические эмбеддинги товаров (768 измерений) через локальную модель
- Двухуровневое ранжирование: FAISS для быстрого поиска кандидатов + CatBoost для ML-ранжирования по признакам
- Сценарный подход: предопределённые наборы категорий для разных видов ремонтных работ (обсудить)
- Система фидбека с байесовским сглаживанием и непрерывным дообучением модели (продумать непрерывное дообучение)
- Дополнительная модель комплементарности категорий для cross-category рекомендаций

Архитектура состоит из двух сервисов с разделением ответственности. Go-бэкенд отвечает за интеграцию с источниками данных магазина.

Разделение позволяет масштабировать и деплоить сервисы независимо, а также переписывать Go-часть (адаптер к конкретной инфраструктуре магазина) без изменений в ML-логике.

**Что убрано по сравнению с хакатоном:** Redis (кэш корзины, JWT-сессии), Elasticsearch (полнотекстовый поиск), весь фронтенд.

## 3. ML Pipeline

### 3.1 Обзор pipeline

[ДИАГРАММА: Блок-схема из 5 последовательных шагов с двумя путями на шаге 2. 1. "Определение сценария". 2а. "Candidate Retrieval: сценарный путь" (группы сценария). 2б. "Candidate Retrieval: семантический путь" (FAISS). 3. "Feature Extraction" (44 признака на каждую пару). 4. "Scoring" (CatBoost ИЛИ формульный fallback). 5. "Top-K отбор".]

На каждый входящий запрос рекомендаций система проходит один и тот же pipeline из пяти шагов. Идея двухуровневого подхода — сначала быстро отобрать небольшой пул кандидатов (100 товаров), а потом точно их отранжировать. Это позволяет держать inference быстрым: FAISS работает за ~1ms, а CatBoost применяется только к 100 кандидатам, а не ко всему каталогу.

**Шаги pipeline для запроса рекомендаций по товару:**

(прописать все сценарии рекомендаций (на карточке товара, в выдаче, в корзине, в сценариях на странице сценария, рекомендации сценариев на основе корзины))

1. **Загрузка товара** — получить данные товара по ID, включая category_id
2. **Определение сценария** — сопоставить category_id с одним из предопределённых сценариев ремонта
3. **Candidate Retrieval:**
   - Если сценарий найден: выбрать до 100 товаров из связанных групп сценария (по 50 из каждой группы)
   - Если сценарий не найден: FAISS nearest-neighbor поиск, топ-100 по семантической близости
4. **Feature Extraction:** для каждой пары (основной товар, кандидат) извлечь 44 признака из 8 групп
5. **Scoring:**
   - При наличии обученной модели: CatBoost Ranker → нормализация в диапазон [0.5, 1.0]
   - Fallback: формульный скоринг на основе весовых коэффициентов
6. **Отбор топ-20** с добавлением rank и match_reasons

### 3.2 Эмбеддинги товаров

Эмбеддинги — это векторные представления товаров в 768-мерном пространстве, где близость векторов отражает семантическую схожесть. "Шпатель стальной 200мм" и "инструмент для нанесения смеси" окажутся близко, потому что нейросеть понимает смысл, а не только буквы. Это ключевой механизм, который позволяет находить релевантные товары даже без истории покупок.

Для каждого товара при генерации формируется текстовое описание, включающее название, путь в иерархии категорий, производителя, описание и характеристики. Это описание передаётся в локальную модель nomic-embed-text через Ollama и получается 768-мерный вектор. Генерация происходит один раз при добавлении или изменении товара — в runtime эмбеддинги уже готовы и хранятся в БД.

#### Формирование текстового представления товара

```python
# build_product_text() — точная реализация из кода
text = f"{name}. Категория: {category_path}. Производитель: {vendor}. {description[:500]}. Характеристики: {params_summary}"
# description обрезается до 500 символов
# params — берутся первые 10 ключ-значение пар
# части объединяются через ". "
```

#### Параметры модели

| Параметр | Значение |
|----------|----------|
| Модель | nomic-embed-text |
| Поставщик | Ollama (локальный inference) |
| Размер модели | 274 MB |
| Размерность вектора | 768 |
| Скорость генерации | ~200 товаров/мин на CPU |
| HTTP timeout | 60 секунд |

#### Хранение

Таблица `product_embeddings`:
- `product_id` (INTEGER, PK) — ссылка на products
- `embedding` (FLOAT[]) — вектор из 768 float значений
- `text_representation` (TEXT) — текст, на основе которого сгенерирован вектор
- `created_at` (TIMESTAMP)

#### Загрузка в память при старте

При старте ML-сервиса все эмбеддинги загружаются из PostgreSQL и строится FAISS-индекс. Это происходит синхронно — сервис не принимает запросы, пока индекс не готов. При ~60k товаров (хакатонные данные) загрузка занимает несколько секунд. При 1M товаров это время и потребление памяти вырастут пропорционально — подробнее в разделе 6.

### 3.3 Candidate Retrieval — FAISS

FAISS (Facebook AI Similarity Search) — специализированная библиотека для поиска ближайших соседей в векторном пространстве. В нашем случае это означает: дан эмбеддинг запрошенного товара, найти топ-k товаров с максимальным косинусным сходством среди всего каталога. FAISS делает это за ~1ms благодаря in-memory индексу — вместо последовательного перебора всех векторов.

#### Конфигурация индекса (текущая реализация)

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| Тип индекса | `IndexFlatIP` | Inner Product на нормализованных векторах = точное косинусное сходство |
| Нормализация | `faiss.normalize_L2()` перед добавлением | Единичная норма, IP становится эквивалентен cosine |
| Размерность | 768 | Соответствует размерности nomic-embed-text |
| Режим поиска | Точный (exhaustive) | При ~60k товаров достаточно быстро |
| k соседей | min(500, len(all_products)) | С запасом для последующей фильтрации до 100 кандидатов |

**Важно при масштабировании до 1M товаров:** `IndexFlatIP` — это точный перебор всех векторов, его время поиска линейно растёт с числом товаров. При 1M товаров поиск займёт ~100ms против ~1ms при 60k. Потребление памяти составит ~3 GB только на индекс (1M × 768 × 4 байта). Это требует перехода на приближённый поиск — `IndexIVFFlat` или `IndexHNSW` — который ускоряет поиск в 50–100 раз ценой небольшой потери точности. Это один из ключевых вопросов для обсуждения при переходе в прод.

#### Два пути candidate retrieval

**Путь A — Сценарный (приоритетный):**
Когда товар принадлежит к одному из известных сценариев ремонта, кандидаты берутся не из FAISS, а из заранее определённых категорий того же сценария. Это гарантирует, что покупателю штукатурки предложат шпатели и грунтовку, а не просто "похожие товары". Для каждой группы сценария (кроме группы самого товара) выбирается до 50 товаров, итого до 100 кандидатов.

**Путь B — Семантический (fallback):**
Для товаров вне сценариев — FAISS поиск k = min(500, total) ближайших соседей. Из результатов исключаются товары той же категории (penalty -0.15 к score), берутся топ-100 по FAISS score.

### 3.4 Feature Engineering — 44 признака

[ДИАГРАММА: Mind-map или таблица из 8 групп признаков с числом признаков в каждой: Семантические (6), Фидбек (8), Ценовые (7), Категорийные (5), Co-purchase (3), Популярность (7), Контекст корзины (3), Комплементарность (5).]

Feature engineering — это процесс превращения сырых данных о паре "основной товар + кандидат" в числовой вектор, который CatBoost использует для ранжирования. 44 признака из 8 групп описывают разные аспекты того, насколько кандидат подходит к основному товару: насколько они похожи семантически, часто ли их покупают вместе, как пользователи оценивали такие рекомендации раньше, насколько кандидат популярен и актуален по цене.

Ключевая идея: ни один признак не является решающим сам по себе — CatBoost находит оптимальные нелинейные зависимости между ними. Например, скидка на кандидата важна только если он дорогой, а co-purchase значим только если пар много. Ручными весами это не уловить.

#### Группа 1: Семантические (6 признаков)

Описывают близость эмбеддингов пары товаров. Несколько метрик расстояния позволяют CatBoost выбирать наиболее информативную в каждом контексте.

| Признак | Формула |
|---------|---------|
| `embedding_cosine_similarity` | dot(norm_a, norm_b) |
| `embedding_l2_distance` | L2 расстояние нормализованных векторов |
| `embedding_dot_product` | dot(norm_a, norm_b) без нормировки |
| `embedding_euclidean_distance` | Евклидово расстояние сырых векторов |
| `embedding_manhattan_distance` | Манхэттенское расстояние |
| `embedding_has_valid` | 1.0 если оба эмбеддинга присутствуют |

*Нормализация:* `vector / (norm(vector) + 1e-8)` — epsilon предотвращает деление на ноль.
*Fallback при отсутствии эмбеддингов:* cosine=0.5, l2=1.0, dot=0.0, euclidean=1.0, manhattan=1.0, has_valid=0.0.

#### Группа 2: Фидбек (8 признаков)

Накопленные оценки пользователей — самый прямой сигнал о качестве рекомендации. Хранятся в агрегированном виде в двух таблицах: `pair_feedback_stats` (оценка конкретной пары товаров) и `scenario_feedback_stats` (оценка товара в контексте сценария). Байесовское сглаживание (Laplace) решает проблему cold start: новый товар с одной оценкой не получает 100% approval, а только 67%.

| Признак | Описание |
|---------|----------|
| `pair_feedback_positive` | Количество лайков для пары товаров |
| `pair_feedback_negative` | Количество дизлайков для пары товаров |
| `pair_feedback_total` | Сумма оценок |
| `pair_feedback_approval_rate` | (positive + 1) / (total + 2) — Laplace smoothing |
| `scenario_feedback_positive` | Лайки в контексте сценария |
| `scenario_feedback_negative` | Дизлайки в контексте сценария |
| `scenario_feedback_total` | Сумма сценарных оценок |
| `scenario_feedback_approval_rate` | (positive + 1) / (total + 2) — Laplace smoothing |

#### Группа 3: Ценовые (7 признаков)

Ценовые признаки отражают ценовой контекст рекомендации. Покупателю дорогого товара, вероятно, подойдут сопутствующие товары того же ценового сегмента. Скидка на кандидата — дополнительный стимул.

| Признак | Формула |
|---------|---------|
| `candidate_price` | Цена кандидата |
| `price_ratio` | candidate_price / max(main_price, 1) |
| `price_diff` | candidate_price - main_price |
| `price_diff_percent` | (price_diff / max(main_price, 1)) * 100 |
| `has_discount` | 1.0 если есть discount_price |
| `discount_percent` | (price - discount_price) / price * 100 |
| `discount_amount` | price - discount_price |

#### Группа 4: Категорийные (5 признаков)

Позиция товаров в иерархии категорий. Товары из одной категории, одного производителя или близких разделов каталога имеют разную природу схожести — CatBoost учится различать, когда это важно.

| Признак | Формула |
|---------|---------|
| `same_category` | 1.0 если category_id совпадает |
| `same_root_category` | 1.0 если совпадает корневая категория |
| `category_distance` | 0.0 — та же корневая, 2.0 — разные корневые |
| `same_vendor` | 1.0 если vendor совпадает |
| `different_vendor` | 1.0 - same_vendor |

*Дерево категорий:* обход через рекурсивный CTE запрос к таблице `categories`.

#### Группа 5: Co-purchase (3 признака)

Статистика совместных покупок из истории заказов — сильнейший сигнал реального спроса. Если товары часто покупают вместе, они, скорее всего, нужны в одном проекте.

| Признак | Формула |
|---------|---------|
| `copurchase_count` | Количество совместных покупок |
| `copurchase_log` | log(1 + copurchase_count) |
| `copurchase_exists` | 1.0 если count > 0 |

#### Группа 6: Популярность товара (7 признаков)

Общая популярность кандидата — косвенный сигнал качества. Товар с тысячами просмотров и заказов более надёжен как рекомендация, чем неизвестная позиция. Счётчики логарифмируются для сглаживания выбросов.

| Признак | Формула |
|---------|---------|
| `has_image` | 1.0 если есть picture |
| `is_discounted` | 1.0 если есть discount_price |
| `price_bucket` | 0: ≤1000 руб, 1: ≤10000 руб, 2: >10000 руб |
| `name_length` | float(len(name)) |
| `view_count` | log(1 + view_count) |
| `cart_add_count` | log(1 + cart_add_count) |
| `order_count` | log(1 + order_count) |

#### Группа 7: Контекст корзины (3 признака)

Если в запросе передаётся текущая корзина покупателя, можно учесть её контекст. Чем ближе кандидат к уже выбранным товарам, тем выше его вероятная релевантность.

| Признак | Описание |
|---------|----------|
| `cart_similarity_max` | Максимальное косинусное сходство с товарами в корзине |
| `cart_similarity_avg` | Среднее косинусное сходство с товарами в корзине |
| `cart_products_count` | Количество товаров в корзине |

*При отсутствии данных о корзине:* все три признака = 0.0.

#### Группа 8: Комплементарность категорий (5 признаков)

Признаки из отдельной модели комплементарности (подробнее в разделе 3.6). Позволяют CatBoost лучше ранжировать товары из других категорий, которые дополняют основной товар.

| Признак | Описание |
|---------|----------|
| `complementarity_score` | Скор модели комплементарности |
| `category_semantic_similarity` | Косинусное сходство эмбеддингов категорий |
| `scenario_category_match` | 0.5 — одна группа сценария (замены), 1.0 — разные группы (дополнения) |
| `copurchase_category_count` | log(1 + co-purchase на уровне категорий) |
| `categories_in_same_scenario` | Количество сценариев, где обе категории присутствуют |

### 3.5 Ранжирование — CatBoost Ranker

CatBoost — алгоритм градиентного бустинга, специально адаптированный для задачи Learning-to-Rank. В отличие от классификации или регрессии, ранкер оптимизирует не точность предсказания отдельного примера, а качество порядка: NDCG@10 измеряет, насколько хорошо релевантные товары оказались в топ-10 выдачи.

Почему именно CatBoost, а не нейросеть: для 44 табличных признаков градиентный бустинг превосходит нейросети по качеству, скорости обучения и интерпретируемости. Нейросети выигрывают на неструктурированных данных (текст, изображения), но для structured data CatBoost/XGBoost — де-факто стандарт.

#### Архитектура модели

| Параметр | Значение |
|----------|----------|
| Алгоритм | CatBoostRanker (Learning-to-Rank) |
| Loss function | YetiRank |
| Eval metric | NDCG:top=10 |
| Custom metrics | NDCG:top=10, PrecisionAt:top=5 |
| Iterations | 500 (по умолчанию, диапазон 100–2000) |
| Learning rate | 0.05 (по умолчанию, диапазон 0.001–0.5) |
| Depth | 6 (по умолчанию, диапазон 3–10) |
| Random seed | 42 |
| use_best_model | True |

#### Схема обучения

[ДИАГРАММА: Схема формирования обучающей выборки. Слева: два источника позитивных примеров — pair_feedback_stats (positive_count ≥ 5) и order_items (copurchase ≥ 2, лимит 10k пар). Справа: два источника негативных — pair_feedback_stats (negative > positive) и hard negatives 3:1. Снизу стрелки ведут к блоку "train/val 80/20 по group_id (main_product_id)".]

Модель обучается на парах (основной товар, кандидат) с бинарными метками. Позитивные примеры — пары, которые пользователи одобряли или покупали вместе. Негативные — явно отвергнутые пары и случайно выбранные товары (hard negatives). Группировка по `main_product_id` обязательна для CatBoost Ranker: модель учится ранжировать кандидатов внутри каждого query, а не глобально.

**Источники обучающих данных:**

| Тип | Источник | Условие | Метка |
|-----|----------|---------|-------|
| Позитивные | `pair_feedback_stats` | positive_count ≥ 5 | y = 1 |
| Позитивные | `order_items` (co-purchase) | совместных покупок ≥ 2, лимит 10 000 пар | y = 1 |
| Негативные | `pair_feedback_stats` | negative_count > positive_count | y = 0 |
| Негативные | Hard negatives | случайные товары, ratio 3:1 к позитивным | y = 0 |

- Разбивка train/val: 80/20 **по уникальным группам** (main_product_id), не по отдельным примерам
- Минимум для обучения: 100 примеров (иначе ошибка)

#### Нормализация выходных скоров

После predict модели скоры нормализуются в диапазон [0.5, 1.0]:
```
normalized = (raw_score - min_score) / score_range
final_score = 0.5 + normalized * 0.5
```
При `score_range == 0` (все кандидаты равнозначны): `final_score = 0.5`.

#### Формульный fallback (при отсутствии обученной модели)

Используется до первого обучения и как аварийный режим. Вручную заданные веса для ключевых сигналов:

```
score = 0.5 (база)
+ semantic_similarity * 0.3   (если есть эмбеддинги)
+ (pair_approval - 0.5) * 0.4 (если есть фидбек)
+ (scenario_approval - 0.5) * 0.2 (если есть сценарный фидбек)
+ discount_percent * 0.1      (если есть скидка)
```
Итоговый score обрезается в диапазон [0, 1].

#### Персистентность модели

- Формат: `.cbm` файлы (CatBoost native binary format)
- Именование: `catboost_ranker_{timestamp}.cbm` (timestamp: `%Y%m%d_%H%M%S`)
- Метаданные: `catboost_ranker_{timestamp}_metadata.json`
- При старте: автоматически загружается последняя модель по дате изменения файла

### 3.6 Комплементарность категорий

Основная проблема cross-category рекомендаций: FAISS по семантическому сходству хорошо находит похожие товары внутри категории ("другая штукатурка"), но плохо справляется с комплементарными товарами из других категорий ("шпатели к штукатурке"). Семантически эти категории разные, но с точки зрения ремонтного проекта — неотделимы.

Для решения этой задачи обучена отдельная модель: LogisticRegression-классификатор, который по эмбеддингам двух категорий предсказывает вероятность их комплементарности. Результаты предвычисляются для всех пар категорий и хранятся in-memory, обеспечивая мгновенный lookup во время inference.

Эти скоры затем поступают как 5 признаков (группа 8) в CatBoost — он учится, в каких ситуациях комплементарность важнее семантического сходства, и ранжирует товары из дополняющих категорий выше.

#### Архитектура модели комплементарности

| Параметр | Значение |
|----------|----------|
| Алгоритм | LogisticRegression (scikit-learn) |
| C (регуляризация) | 1.0 |
| class_weight | balanced (компенсирует дисбаланс классов) |
| max_iter | 1000 |
| random_state | 42 |

#### Вычисление эмбеддингов категорий

Эмбеддинг категории вычисляется как среднее арифметическое эмбеддингов всех товаров в ней (`np.mean`, тип `np.float32`). Это позволяет описать "типичный товар" категории одним вектором без дополнительного inference в Ollama.

#### Feature vector для пары категорий (размерность 4×768 + 1 = 3073)

```python
emb1_norm = emb1 / (norm(emb1) + 1e-8)
emb2_norm = emb2 / (norm(emb2) + 1e-8)
diff    = emb1_norm - emb2_norm           # вектор разности
product = emb1_norm * emb2_norm           # поэлементное произведение
cosine  = dot(emb1_norm, emb2_norm)       # скалярное сходство
features = concat([emb1_norm, emb2_norm, diff, product, [cosine]])
```

#### Обучающие данные и персистентность

- Источник: файл `recommendations/data/complementary_categories.csv`
- Формат: `category_id_1, category_id_2, is_complementary, relation_type`
- Разбивка: train/test 80/20, stratify=y, нормализация StandardScaler
- После обучения: 4 pickle-файла (`model`, `scaler`, `matrix`, `type_map`) в директории `models/`

## 4. Данные и обучение

### 4.1 Схема ML-таблиц

[ДИАГРАММА: ER-диаграмма ML-таблиц. `products` как центральная сущность. От неё отходят: product_embeddings (1:1), product_stats (1:1), copurchase_stats (M:N через product_id_1/2), product_pair_feedback (M:N), pair_feedback_stats (агрегат pair_feedback). Отдельный кластер: scenario_feedback и scenario_feedback_stats (связаны только через product_id, без FK). recommendation_events отдельно (M:N с products).]

Схема данных разделена на две логические группы. Первая — данные о самих товарах: эмбеддинги, статистика поведения, co-purchase. Вторая — обратная связь от пользователей: сырые события фидбека и их агрегации. Такое разделение важно: агрегированные таблицы (`pair_feedback_stats`, `scenario_feedback_stats`) используются при каждом запросе рекомендаций, а сырые (`product_pair_feedback`, `recommendation_events`) — для аналитики и обучения.

**ML-таблицы и их назначение:**

| Таблица | Назначение | Ключевые поля |
|---------|------------|---------------|
| `product_embeddings` | Векторные представления товаров | product_id (PK), embedding (FLOAT[]) |
| `product_stats` | Поведенческая статистика | product_id (PK), view_count, cart_add_count, order_count |
| `copurchase_stats` | Статистика совместных покупок | product_id_1, product_id_2 (PK), copurchase_count |
| `product_pair_feedback` | Сырой фидбек на пары товаров | id, main_product_id, recommended_product_id, feedback_type |
| `pair_feedback_stats` | Агрегированный фидбек на пары | main_product_id + recommended_product_id (PK), positive_count, negative_count |
| `scenario_feedback` | Сырой фидбек в контексте сценария | id, scenario_id, group_name, product_id, feedback_type |
| `scenario_feedback_stats` | Агрегированный сценарный фидбек | (scenario_id, group_name, product_id) UNIQUE, positive_count, negative_count |
| `recommendation_events` | События взаимодействия с рекомендациями | user_id/session_id, event_type, main/recommended product, rank |

### 4.2 Источники сигналов для обучения

Система использует три типа сигналов, нарастающих по ценности по мере накопления.

**Co-purchase из истории заказов** — сильнейший сигнал, не требует участия пользователя. Для каждого заказа с 2+ товарами генерируются все пары комбинаций. Пары симметричны: key = (min(id1, id2), max(id1, id2)). Обновление через полный пересчёт (TRUNCATE + reload). Минимальный порог для включения в обучение: copurchase_count ≥ 2.

**Явный фидбек** — пользователь оценил рекомендацию как положительную или отрицательную. Два типа: pair feedback (оценка конкретной пары товаров) и scenario feedback (оценка товара в контексте группы сценария). Хранится в сырых таблицах и агрегируется через UPSERT с `ON CONFLICT DO UPDATE SET count = count + 1`.

**Поведенческие события** — impression (показ), click (клик), add_to_cart (добавление в корзину). Сейчас записываются в `recommendation_events`, но не используются напрямую в обучении — это задел для будущего обогащения модели неявными сигналами. Требуют user_id или session_id.

### 4.3 Cold Start и синтетический фидбек

При первом запуске системы нет ни истории покупок, ни реального фидбека — CatBoost не на чём обучать. Скрипт `generate_synthetic_feedback.py` решает эту проблему, создавая начальный фидбек на основе семантического сходства.

**Алгоритм:**
- Позитивные пары (70% = 350 из 500): два товара из одной категории с cosine_similarity > 0.3. positive_count = random(3, 15)
- Негативные пары (30% = 150 из 500): два товара из разных категорий. negative_count = random(2, 8)
- Исходные данные: до 5000 товаров с эмбеддингами из БД

**Ограничение:** синтетический фидбек создаёт смещение — модель, обученная только на нём, переоценивает внутрикатегорийное сходство. Он служит стартовой точкой; при накоплении реального фидбека и co-purchase данных модель следует переобучить.

### 4.4 Сценарии ремонта

Сценарий — это предопределённый набор групп категорий товаров, нужных для конкретного вида ремонтных работ. Сценарии решают две задачи одновременно: при запросе рекомендаций для товара из сценария кандидаты берутся именно из его категорий (не из FAISS), а при показе рекомендаций для корзины система отображает прогресс покупателя — какие группы уже закрыты, чего не хватает.

Каждая группа внутри сценария может быть обязательной или опциональной. При определении прогресса считаются только обязательные группы. Если все обязательные закрыты, система предлагает альтернативы (похожие товары из тех же категорий) со скором 0.7.

| ID | Название | Всего групп | Обязательных |
|----|----------|-------------|--------------|
| `floor` | Монтаж наливного пола | 8 | 5 |
| `partitions` | Монтаж перегородок | 7 | 7 |
| `walls` | Выравнивание стен | 8 | 7 |
| `tiling` | Укладка плитки | 10 | 7 |
| `electrical` | Электромонтаж | 8 | 7 |

**Пример структуры сценария `walls` — Выравнивание стен:**

| Группа | Category IDs | Обязательна |
|--------|-------------|-------------|
| Штукатурка гипсовая | [25178] | Да |
| Грунтовки | [25380] | Да |
| Шпатлёвки | [25179, 30462] | Да |
| Ёмкости строительные | [25252] | Да |
| Правила | [23705] | Да |
| Шпатели | [30226] | Да |
| Насадки для миксеров | [29165] | Да |
| Сетки малярные, серпянка | [30229] | Нет |

*Замечание:* текущие category ID привязаны к хакатонному каталогу МАКСИДОМ и потребуют актуализации под реальный каталог.

### 4.5 Процесс переобучения CatBoost

Переобучение запускается вручную или по расписанию через `POST /ml/train`. Принимает параметры (iterations, learning_rate, depth, min_feedback_count), читает текущее состояние PostgreSQL и обучает новую модель. После успешного обучения модель сохраняется на диск и загружается в память — старая модель заменяется без перезапуска сервиса.

| Параметр | По умолчанию | Диапазон |
|----------|-------------|---------|
| iterations | 500 | 100–2000 |
| learning_rate | 0.05 | 0.001–0.5 |
| depth | 6 | 3–10 |
| min_feedback_count | 5 | 1–20 |

**Время обучения:** 1–5 минут в зависимости от объёма данных.

## 6. Производительность и надёжность

### 6.1 Latency по шагам pipeline

| Операция | Время | Примечание |
|----------|-------|------------|
| FAISS search (k=100) | ~1ms | In-memory, IndexFlatIP, ~60k товаров |
| Feature extraction (44 признака × 100 кандидатов) | ~10ms | Batch SQL запросы |
| CatBoost predict (100 кандидатов) | ~50ms | CPU inference |
| Полный цикл рекомендаций | < 100ms | Без сетевых задержек |
| Генерация одного эмбеддинга (Ollama) | 50–200ms | Только при добавлении нового товара |

### 6.2 Масштабирование до 1M товаров

Текущая реализация оптимизирована для ~60k товаров. При переходе к 1M возникают два ключевых ограничения:

**FAISS IndexFlatIP при 1M товаров:**
- Потребление памяти: 1M × 768 × 4 байта ≈ **3 GB** только на индекс
- Время поиска: ~100ms (против ~1ms при 60k) — линейная зависимость от размера
- Решение: переход на `IndexIVFFlat` или `IndexHNSW` — приближённый поиск, ускорение в 50–100 раз при потере точности < 5%

**Хранение эмбеддингов в PostgreSQL:**
- 1M × 768 float ≈ 3 GB в таблице `product_embeddings`
- При загрузке в память при старте нужно передать весь объём через сеть
- Потенциальное решение: pgvector для хранения и поиска без отдельного FAISS, или предзагруженный FAISS-индекс на диске

*Требует обсуждения с тимлидом: какое железо будет доступно и каков допустимый latency.*

### 6.3 Поведение при деградации

Система спроектирована с несколькими уровнями fallback — деградация graceful, без hard failure:

| Ситуация | Поведение |
|----------|-----------|
| CatBoost модель не обучена | Формульный скоринг (fallback) |
| Эмбеддинг товара отсутствует | Фиксированные значения: cosine=0.5, l2=1.0 |
| Нет фидбека для пары | pair_approval_rate = 0.5 (нейтрально, Laplace) |
| Товар вне сценария, нет эмбеддинга | Пустой результат |
| Complementarity model не загружена | Признаки комплементарности = 0 |
