# Целевой вариант: рекомендации товаров в корзине

## 1. Что делаем

Систему рекомендаций товаров для корзины магазина строительных материалов.

Пользователь видит только список рекомендованных товаров — без сценариев, групп и прогресс-баров. Сценарии — внутренняя сущность системы: создаются менеджерами магазина через админку, определяются автоматически по корзине, используются как внутренний контекст для retrieval и ranking.

## 2. Целевой pipeline

1. Пользователь открывает корзину.
2. Система автоматически определяет наиболее подходящий сценарий по составу корзины.
3. Для каждой незакрытой группы сценария собирается широкий пул кандидатов из нескольких каналов.
4. Кандидаты ранжируются ML-моделью в контексте `(корзина, сценарий, группа)`.
5. Результаты по всем группам объединяются в один плоский список, дедуплицируются.
6. Пользователь видит список рекомендованных товаров.
7. Все показы и действия логируются и используются в обучении.

## 3. Архитектура

Два сервиса: **Go backend / Data API** и **Python ML service**.

Go backend отвечает за: синхронизацию каталога из Oracle через события, хранение локальной копии данных, управление сценариями через админку, сбор событий и фидбека, отдачу API клиентам.

Python ML service отвечает за: определение сценария по корзине, подбор кандидатов, ранжирование, работу с эмбеддингами, обучение моделей.

Данные организованы в три слоя:
- **Raw events** — сырые факты (заказы, показы, действия). Append-only, источник правды.
- **Features / Aggregates** — предрассчитанные агрегаты: product_features (7d), copurchase_stats, category_relations. Пересчитываются по расписанию.
- **Online serving** — данные в памяти ML-сервиса: FAISS-индекс, матрица комплементарности, CatBoost-модель.

## 4. Известные параметры системы

| Параметр | Значение                                                         |
|----------|------------------------------------------------------------------|
| Источник каталога | Oracle БД магазина, синхронизация через события, почти real-time |
| История заказов | Доступна, используется для co-purchase                           |
| Масштаб каталога | ~90k товаров сейчас, до 1М в перспективе                         |
| Эмбеддинги | Ollama + nomic-embed-text, 768-мерные векторы                    |
| Владелец сценариев | Менеджеры магазина через админку                                 |

## 5. Сценарии как данные (внутренняя сущность)

Сценарии хранятся в БД, не в коде. Управляются через админку менеджерами магазина.

**Workflow:** `draft` → редактирование групп и весов → `active` (начинает использоваться) → `archived`. Черновик не влияет на живые рекомендации.

Для сценария хранятся: `scenario_id`, название, описание, статус, версия.

Для группы сценария хранятся: название (внутреннее), обязательность, порядок.

Для каждой категории в группе хранится **вес** (0.0–1.0) — насколько категория типична для этой группы.

## 6. Определение сценария по корзине

Это единственный путь. Пользователь не выбирает сценарий явно.

### Стартовая версия: взвешенное покрытие групп

Для каждого активного сценария считается покрытие обязательных групп категориями товаров из корзины. Веса категорий из `scenario_group_category_weights` дают более точный скор, чем бинарное попадание.

Если корзина не соответствует ни одному сценарию с достаточной уверенностью — рекомендации не показываются. Порог уверенности подбирается эмпирически (~0.15–0.2).

### Целевое улучшение: дополнительные сигналы

- **Эмбеддинг-скоринг:** cosine similarity среднего эмбеддинга корзины с эталонными эмбеддингами сценария.
- **Co-purchase сигнал:** товары корзины часто покупаются с товарами групп сценария.
- **Комплементарность:** категории корзины комплементарны категориям сценария.
- **Классификатор:** LogisticRegression или small CatBoost, обученный на данных `(cart → scenario)`.

Автоопределение — ключевой компонент. От его точности зависит релевантность всех рекомендаций.

## 7. Retrieval

Для каждой незакрытой группы параллельно запускаются несколько каналов подбора кандидатов.

### 7.1 Каналы

- **Group popularity:** товары нужных категорий, отсортированные по `popularity_score` (взвешенный агрегат из views, clicks, cart_adds, purchases за 7 дней).
- **Basket-to-item embedding:** FAISS-поиск по среднему эмбеддингу корзины, фильтрация по категориям группы.
- **Co-purchase:** товары, которые часто покупают вместе с товарами корзины. Ранжирование по `lift`, а не по абсолютной частоте.
- **Complementarity:** товары из категорий, которые модель комплементарности считает дополняющими к категориям корзины.
- **Scenario prior:** что чаще выбирают для закрытия этой группы в этом сценарии (накапливается из логов показов).

Фильтрация во всех каналах: `available = true` + региональный сток из `product_availability`.

### 7.2 Слияние кандидатов

До ML-ранкера используется **Reciprocal Rank Fusion**: `score = \sum 1/(60 + rank_in_channel)`. Не требует нормализации скоров между каналами, работает как надёжный baseline.

Для каждого кандидата сохраняются его источники и ранги в каждом канале — они становятся признаками для ML-ранкера.

## 8. Ranking

### 8.1 Два режима

**RRF-режим (фазы 0–1):** кандидаты ранжируются по RRF score. Не требует обучения, работает с первого дня.

**ML-режим (фаза 2+):** CatBoostRanker, отдельная модель для задачи `(корзина, сценарий, группа) → товар`. Не та же модель, что рекомендации на карточке товара.

### 8.2 Признаки ранкера (~30 штук)

**Basket-candidate** (взаимодействие кандидата с корзиной):
- cosine similarity кандидата со средним/максимальным эмбеддингом корзины
- max lift и max confidence co-purchase кандидата с товарами корзины
- совпадение бренда с корзиной
- соотношение цены кандидата к медиане корзины

**Retrieval-source** (из каких каналов пришёл кандидат):
- бинарные флаги по 5 каналам
- ранг в каждом канале
- RRF score

**Candidate** (свойства товара):
- цена, наличие скидки, процент скидки
- popularity_score, CTR за 7 дней, conversion_rate за 7 дней
- частота выбора этого товара в этой группе этого сценария
- complementarity_score к категориям корзины

### 8.3 Жёсткие правила поверх ML

Слой бизнес-правил применяется после ранжирования. Правила редактируются через админку. Пример: "Если в корзине цементная штукатурка — не рекомендовать гипсовую шпатлёвку".

## 9. Итоговый список

Результаты по всем незакрытым группам объединяются в один плоский список:
- дедупликация: если товар подходит нескольким группам — показывается один раз с наибольшим score;
- сортировка по score;
- при необходимости — диверсификация, чтобы товары из разных групп чередовались.

Пользователь видит единый список рекомендованных товаров без группировки по сценарным группам.

## 10. Альтернативы

Режим замены товара. Пользователь хочет найти аналог для конкретного товара в корзине (другой бренд, другая цена).

Retrieval: embedding similarity + co-purchase (что покупают вместо этого товара) + popularity в той же категории.

Ranking: тот же CatBoostRanker с дополнительными признаками — сходство с заменяемым товаром, соотношение цен, флаг другого бренда.

API: `GET /api/alternatives?product_id=456&cart=1,2,3`

## 11. Логирование показов и обратная связь

Критически важно: без логов с контекстом корзины обучение ранкера невозможно.

**Impression** создаётся сервером автоматически при генерации рекомендаций. На каждую незакрытую группу — отдельная запись. Все impressions одного запроса объединены `request_id`. Хранится: снимок корзины, список кандидатов с позициями и скорами, метод ранжирования, версия сценария.

**Действия пользователя** (click, add_to_cart) — фронт отправляет `POST /api/events` с `request_id` и `product_id`. в очередь, не блокирует UI.

**Покупка** привязывается сервером при оформлении заказа: приоритет через предыдущие действия (impression известен), иначе — поиск в impressions по session_id + окно 24 часа.

**Сигналы для обучения:**

| Сигнал | Ценность |
|--------|----------|
| Impression (показ) | Базовый — знаем что показали |
| Click | Слабый позитив, подвержен position bias |
| Add-to-cart | Средний позитив |
| Purchase | Сильный позитив |
| Co-purchase из заказов | Офлайн-сигнал для retrieval и cold start |

## 12. Обучение ранкера

Каждый обучающий пример: при таком состоянии корзины, в таком сценарии, для такой группы — насколько хорош этот кандидат.

**Метки релевантности:** 3 = покупка, 2 = add_to_cart, 1 = клик, 0 = показан но проигнорирован.

**Hard negatives:** случайные товары из категорий группы, не попавшие в показ. Соотношение ~3:1 к позитивам.

**Position bias correction:** позиция добавляется как признак при обучении, фиксируется в 1 при inference.

## 13. Cold start и поэтапный запуск

### Фаза 0 — подготовка до запуска
- Загрузить каталог (~90k товаров), сгенерировать эмбеддинги через Ollama
- Посчитать co-purchase из истории заказов Oracle
- Обучить модель комплементарности на парах категорий
- Настроить сценарии и группы в БД через админку
- Сгенерировать синтетический scenario prior из co-purchase

### Фаза 1 — запуск с RRF
RRF-ранкер в проде. Собираем логи показов и действий пользователей.

### Фаза 2 — первый ML-ранкер
Обучаем CatBoost на накопленных логах (~1000+ impressions с действиями). A/B тест: 90% RRF, 10% ML. Постепенно увеличиваем долю ML.

### Фаза 3 — итерации
Регулярное переобучение. Улучшение автоопределения сценария. Расширение признаков.

## 14. Итоговый целевой вариант

- Сценарии — скрытая внутренняя сущность, управляются менеджерами через админку с поддержкой черновиков
- Сценарий определяется автоматически по корзине с оценкой уверенности; пользователь не выбирает сценарий
- Пользователь видит единый список рекомендованных товаров без группировки
- Retrieval строится из 5 каналов с учётом региональных стоков, кандидаты сливаются через RRF
- Ranking — отдельный CatBoostRanker для задачи рекомендаций в корзине
- До появления ML-модели RRF уже даёт качество лучше формульного
- Все показы логируются со снимком корзины и версией сценария
- Обучение включает коррекцию position bias и hard negatives
- Каталог синхронизируется из Oracle через события; региональные стоки учитываются как обязательный фильтр
- Система работает поэтапно: сначала RRF, затем ML, затем итерации
