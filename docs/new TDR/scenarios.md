# План улучшения рекомендаций для сценариев

## 1. Зачем нужен этот документ

Этот документ описывает, как перевести текущие рекомендации для сценариев ремонта из демо-логики в production-ready систему.

Сейчас сценарные рекомендации работают по упрощённой схеме:

1. Для каждой незакрытой группы сценария берутся товары прямым SQL-запросом по `category_id`.
2. Из БД выбираются первые `N` товаров (`ORDER BY p.id LIMIT 100`).
3. Поверх этого фиксированного пула считается формульный score:
   - `cart_similarity`
   - `scenario_feedback`
   - `discount`
4. Возвращается top-k.

Проблема не в самой формуле, а в том, что она ранжирует уже слабый пул кандидатов. Если retrieval плохой, ranker не спасёт. В production для такого кейса нужен отдельный pipeline для cart/scenario рекомендаций, а не SQL-выборка первых товаров из группы.

---

## 2. Что именно не так в текущей реализации

### 2.1. Candidate retrieval слишком слабый

- Кандидаты берутся только из `get_products_by_categories(...)`.
- Внутри группы это детерминированный пул: фактически "первые 100 доступных товаров".
- Нет retrieval по контексту корзины.
- Нет retrieval по co-purchase графу.
- Нет retrieval по комплементарности категорий.
- Нет retrieval по популярности в рамках сценария и группы.
- Нет отдельного retrieval по "заменам" и по "дополнениям".

Следствие: рекомендации часто будут повторяться, а персонализация будет слабой даже при хорошем скоринге.

### 2.2. Ranker не соответствует задаче

Сейчас сценарный ranker не ML-модель, а формула. Это приемлемо как fallback, но не как основа production-логики.

Проблемы:

- Нет отдельной модели для запроса вида `(корзина, сценарий, группа) -> товар`.
- Не используется текущая инфраструктура CatBoost для Типа 2.
- Не используются признаки комплементарности, хотя именно они нужны для cross-category сценариев.
- Не учитываются business-сигналы: наличие, популярность в группе, ценовой диапазон, брендовая диверсификация, вероятность закрыть группу.

### 2.3. Модель запроса слишком грубая

Сейчас контекст корзины сводится к `max cosine_similarity` между кандидатом и любым товаром в корзине.

Этого недостаточно, потому что:

- в корзине может быть несколько разных намерений одновременно;
- пользователь может идти по нескольким стадиям ремонта;
- корзина может содержать товары из разных сценариев;
- комплементарные товары могут быть семантически далеки, но функционально обязательны.

### 2.4. Сценарные данные пока не готовы для обучения сильной модели

Сейчас есть `scenario_feedback_stats` и общие события рекомендаций, но для production-ранжирования этого мало.

Не хватает:

- логов показов по каждой группе сценария;
- информации, какой именно пул кандидатов показывался;
- событий click / add_to_cart / order в разрезе `scenario_id + group_name + cart_snapshot`;
- данных для hard negative mining;
- стабильного идентификатора запроса: `session_id` / `cart_snapshot_id` / `query_id`.

## 3. Что делают похожие открытые решения

Ниже не список "что надо слепо копировать", а паттерны, которые повторяются в открытых production и research решениях.

### 3.1. Почти везде используется двухэтапная схема: retrieval + ranking

Идея стандартная:

1. Быстро собрать широкий, но релевантный пул кандидатов.
2. Затем точнее переранжировать его более тяжёлой моделью.

Это подтверждается и индустриальными библиотеками, и практикой production recommender systems.

Для нашего кейса ключевой вывод такой: нельзя рассматривать сценарные рекомендации как "SQL плюс формула". Нужен отдельный retrieval stage для корзинного контекста.

### 3.2. Для корзины и сессии обычно строят отдельную модель намерения

В открытых решениях для session-based и basket-based recommendation общий паттерн такой:

- запросом является не один товар, а последовательность или набор товаров;
- модель должна понимать текущее намерение пользователя;
- для анонимных пользователей основным источником сигнала является сама текущая корзина / сессия.

Для нас это значит:

- для Типа 2 нужно моделировать не `main_product_id`, а `cart context`;
- позже это логично развивать в basket encoder / session encoder;
- на первом production-этапе можно начать не с нейросети, а с хорошего гибридного retrieval и CatBoost ranker.

### 3.3. Для within-basket и complementary recommendation часто смешивают несколько источников кандидатов

Сильные решения обычно не зависят от одного канала retrieval.

Типичные каналы:

- item-to-item similarity;
- basket-to-item similarity;
- co-purchase;
- association / graph-based neighborhood;
- popularity priors внутри сегмента;
- metadata/content-based matching;
- rules или business constraints.

Это особенно важно в нашем кейсе, потому что сценарная рекомендация должна одновременно решать две разные задачи:

- закрыть недостающую группу;
- подобрать внутри этой группы лучший товар под текущую корзину.

### 3.4. Bundle / basket рекомендации рассматриваются как отдельная задача, а не как обычный item-to-item

В research по bundle recommendation и within-basket recommendation это отдельный класс задач:

- есть множественные намерения внутри одной корзины;
- есть зависимость между уже выбранными товарами;
- релевантность кандидата определяется не одной парой, а всем состоянием корзины.

Для нас это сильный аргумент в пользу отдельного ranker и отдельного набора обучающих данных для Типа 2.

### 3.5. Глубокие модели дают выигрыш, но обычно после того, как уже решены данные и retrieval

Open-source библиотеки и статьи показывают, что sequential / basket модели дают хороший результат, но только если:

- есть достаточный объём сессионных событий;
- корректно собраны positive / negative примеры;
- настроен retrieval;
- есть стабильный pipeline обновления индексов и embeddings.

Поэтому для вашей системы не стоит начинать с GNN или Transformer как с первого шага. Прагматичнее сначала построить нормальный гибридный retrieval и scenario-specific CatBoost ranker.

## 4. Рекомендованная целевая схема для сценарных рекомендаций

### 4.1. Целевой pipeline

Для каждой незакрытой группы сценария:

1. Получить контекст запроса:
   - `scenario_id`
   - `group_name`
   - `cart_product_ids`
   - агрегаты по корзине

2. Собрать кандидатов из нескольких каналов retrieval.

3. Объединить кандидатов в единый пул.

4. Для каждого кандидата посчитать признаки.

5. Пропустить кандидатов через отдельный ranker для сценариев.

6. Применить post-processing:
   - dedup;
   - diversity;
   - ограничения по бренду / цене / availability;
   - объяснимые reasons.

7. Вернуть top-k.

### 4.2. Retrieval должен стать гибридным

Вместо одного SQL-источника нужен multi-source retrieval. Практический вариант:

#### Канал A. Group-constrained popularity retrieval

Базовый качественный канал, который всегда нужен:

- товары группы, доступные к продаже;
- сортировка не по `id`, а по бизнес-приоритету:
  - `order_count`
  - `cart_add_count`
  - `view_count`
  - свежесть
  - наличие
  - скидка

Это не персонализация, но хороший baseline-пул.

#### Канал B. Basket-to-item embedding retrieval

Вместо выбора первых товаров из группы:

- сформировать embedding корзины;
- искать товары, близкие к корзинному контексту;
- затем фильтровать по нужной группе сценария.

На первом этапе basket embedding можно считать просто:

- `mean(cart_embeddings)`;
- `max pooling`;
- либо несколько sub-query векторов по товарам корзины.

Это уже заметно лучше, чем текущий SQL-only retrieval.

#### Канал C. Co-purchase retrieval

Собирать кандидатов, которые часто покупают вместе с любым товаром из корзины:

- по каждому товару корзины получить top co-purchase соседей;
- объединить;
- оставить только товары нужной группы.

Это сильный канал для функционально дополняющих товаров.

#### Канал D. Complementarity retrieval

Использовать текущую модель комплементарности не только как feature для ранжирования, но и как retrieval source:

- взять категории товаров из корзины;
- оценить их комплементарность к категориям группы;
- поднять кандидатов из наиболее комплементарных категорий и брендов.

Это особенно важно там, где cosine similarity работает плохо.

#### Канал E. Scenario/group prior retrieval

Нужен отдельный prior внутри каждой группы:

- наиболее часто выбираемые товары для `scenario_id + group_name`;
- товары с высоким `scenario_feedback_approval`;
- товары с высокой конверсией показа в add-to-cart / order.

Это поможет стабилизировать качество даже при слабом персональном сигнале.

### 4.3. Не один пул, а union кандидатов

Рекомендуемая схема:

- из каждого канала брать top 50-150 кандидатов;
- объединять через union;
- дедуплицировать;
- сохранять source features:
  - `from_popularity`
  - `from_embedding`
  - `from_copurchase`
  - `from_complementarity`
  - `from_scenario_prior`
- итоговый пул на ranker: 200-500 кандидатов на группу.

Это стандартный production pattern: лучший top-k почти всегда получается не из одного retrieval-канала.

## 5. Какой ranker нужен для Типа 2

### 5.1. Нужна отдельная модель под задачу `(корзина, сценарий, группа) -> товар`

Лучший практический вариант для первого production-этапа:

- отдельный `CatBoostRanker` или `LightGBM LambdaMART`;
- query = `cart_snapshot + scenario_id + group_name`;
- label = пользователь выбрал / не выбрал товар для этой группы.

Не стоит пытаться переиспользовать текущий ranker без изменения обучающей схемы. У него другая постановка задачи: `(main_product, candidate)`.

### 5.2. Почему CatBoost здесь хороший первый шаг

Потому что:

- у вас уже есть CatBoost-инфраструктура;
- у вас табличные признаки, а не end-to-end нейронный pipeline;
- CatBoost хорошо работает на смеси dense/sparse/business признаков;
- его проще дебажить, валидировать и выкатывать;
- на этапе перехода в прод он даст лучший time-to-value, чем GNN/Transformer.

### 5.3. Какие признаки нужны новому scenario ranker

#### Блок 1. Basket-to-candidate similarity

- max similarity к товарам в корзине;
- avg similarity;
- similarity к mean embedding корзины;
- similarity к товарам той части корзины, которая ближе всего к текущей группе;
- similarity к товарам из уже закрытых обязательных групп.

#### Блок 2. Complementarity

- complementarity_score между категориями корзины и кандидатом;
- max / avg complementarity по корзине;
- наличие связи между группой кандидата и уже закрытыми группами сценария;
- признак "дополняет обязательную незакрытую часть сценария".

#### Блок 3. Co-purchase / graph features

- max co-purchase count с любым товаром корзины;
- sum co-purchase counts;
- число товаров корзины, с которыми есть co-purchase связь;
- co-purchase на уровне категорий.

#### Блок 4. Scenario performance features

- `scenario_feedback_approval_rate`;
- CTR / add-to-cart rate в данной группе;
- order conversion rate внутри группы;
- частота выбора товара в сценарии;
- popularity percentile внутри группы.

#### Блок 5. Business / catalog features

- наличие;
- цена;
- discount;
- brand / vendor;
- ценовой bucket;
- margin, если бизнес даст;
- наличие изображения / полнота карточки;
- freshness / age of SKU.

#### Блок 6. Query-level features

- размер корзины;
- сколько обязательных групп уже закрыто;
- прогресс по сценарию;
- есть ли смешение нескольких сценариев в корзине;
- confidence определения сценария;
- номер группы в сценарии;
- обязательная / опциональная группа.

#### Блок 7. Retrieval source features

- score из embedding retrieval;
- score из co-purchase retrieval;
- score из complementarity retrieval;
- score из popularity prior;
- количество каналов, которыми найден кандидат.

Это очень полезный production pattern: ranker часто лучше работает, когда знает, из каких retrieval-каналов пришёл кандидат.

## 6. Как собрать данные для обучения scenario ranker

### 6.1. Что считать query

Нужен стабильный идентификатор запроса. Практический вариант:

- `query_id = hash(session_id, scenario_id, group_name, cart_snapshot)`

Где `cart_snapshot`:

- отсортированный список `product_id` в корзине на момент показа;
- или отдельная сущность `cart_snapshot_id`.

### 6.2. Что считать позитивом

Позитивный пример для `scenario_id + group_name`:

- товар был показан и затем добавлен в корзину;
- товар был куплен в том же сценарном контексте;
- товар получил явный positive feedback;
- товар был выбран вместо других показанных кандидатов этой группы.

Лучше использовать иерархию лейблов:

- `purchase` > `add_to_cart` > `click` > `impression only`

### 6.3. Что считать негативом

Негативы должны быть не случайными, а осмысленными:

- показали, но не кликнули;
- кликнули, но не добавили;
- показали и пользователь выбрал другой товар из той же группы;
- hard negatives из этой же группы и близкого ценового диапазона.

Для ranking-задачи это лучше, чем просто случайные товары из каталога.

### 6.4. Как делать train/val split

Нужен time-based split, а не случайный.

Причина:

- в проде модель предсказывает будущее, а не прошлое вперемешку;
- случайный split даёт leakage;
- особенно опасно это для popularity и scenario stats.

Рекомендуется:

- train на окне `T0..T1`;
- validation на `T1..T2`;
- отдельный offline backtest на самых свежих данных.

## 7. Что нужно изменить в данных и backend

### 7.1. Расширить логирование сценарных показов

Сейчас для сильного scenario ranker не хватает детального exposure log.

Нужно писать:

- `query_id`
- `session_id` / `user_id`
- `scenario_id`
- `group_name`
- `cart_snapshot_id`
- список показанных кандидатов
- позицию кандидата
- score и retrieval sources
- timestamp

### 7.2. Расширить логирование действий после показа

Нужно связывать показ и действие:

- impression
- click
- add_to_cart
- remove_from_cart
- order
- explicit positive / negative feedback

Без этого не получится корректный learning-to-rank dataset.

### 7.3. Вынести сценарии из hardcode в БД

Это не обязательно для первой итерации улучшения качества, но обязательно для production-эксплуатации.

Рекомендуемые таблицы:

- `scenarios`
- `scenario_groups`
- `scenario_group_categories`
- `scenario_group_rules`
- `scenario_group_priorities`

Плюсы:

- можно менять сценарии без релиза Python-сервиса;
- можно версионировать сценарии;
- можно строить аналитику по сценариям;
- можно управлять обязательностью и порядком групп из админки.

### 7.4. Нужен pipeline обновления retrieval индексов

Если использовать embedding retrieval для сценариев, нужен не только `product_embeddings`, но и обновление serving-индекса:

- batch rebuild;
- либо incremental upsert в ANN-индекс;
- либо переход на `pgvector` / HNSW в PostgreSQL, если это лучше ложится в infra.

Для production важно, чтобы новые товары попадали в retrieval без ручного перезапуска сервиса.

## 8. Рекомендуемый roadmap внедрения

### Этап 0. Быстрые улучшения без смены архитектуры

Срок: короткий, низкий риск.

Что сделать:

- убрать `ORDER BY p.id`;
- сортировать внутри группы по availability + popularity + scenario feedback;
- собирать не один SQL-пул, а минимум 3:
  - popular
  - discounted
  - high scenario approval
- объединять кандидатов и дедуплицировать;
- добавить diversity constraints:
  - не больше `N` товаров одного бренда подряд;
  - разный ценовой диапазон;
  - не только один и тот же SKU-family;
- показывать альтернативы не только когда все группы закрыты.

Что это даст:

- уберёт самый грубый дефект текущего решения;
- снизит однообразие выдачи;
- даст более адекватный baseline перед следующими этапами.

### Этап 1. Гибридный retrieval для сценариев

Срок: средний.

Что сделать:

- добавить basket-to-item retrieval по embeddings;
- добавить co-purchase retrieval;
- добавить complementarity retrieval;
- оставить popularity retrieval как safety-net;
- собирать union кандидатов 200-500 на группу.

Практический компромисс:

- не строить сразу отдельный basket encoder;
- начать с `mean/max` по embeddings корзины и агрегации по co-purchase;
- уже на этом этапе можно получить большой прирост относительно SQL-only.

### Этап 2. Scenario-specific CatBoost ranker

Срок: средний.

Что сделать:

- завести `query_id`;
- наладить сбор exposure/action данных;
- собрать dataset для `(cart_snapshot, scenario_id, group_name, candidate)`;
- обучить отдельный ranker;
- запустить shadow mode и offline evaluation.

Почему это важнее, чем сразу нейросеть:

- это кратчайший путь к production-grade качеству;
- позволяет переиспользовать текущий стек;
- проще защищать на архитектурном ревью.

### Этап 3. Улучшенный cart encoder

Срок: средний или длинный, зависит от данных.

Когда делать:

- когда накопится достаточно сессионных событий;
- когда станет видно, что CatBoost упирается в качество basket representation.

Что делать:

- two-tower модель `basket -> item`;
- либо session-based model: GRU / Transformer;
- retrieval через ANN по learned basket embedding;
- ranker оставить отдельным вторым этапом.

Это уже ближе к сильным open solutions для within-basket recommendation.

### Этап 4. Онлайн-оптимизация и exploration

Срок: длинный.

Что делать:

- A/B тесты;
- bandit-style reranking;
- controlled exploration новых товаров;
- оптимизация не только по CTR, но и по group completion / attach rate / order uplift.

## 9. Что я рекомендую как основной путь для этого проекта

### 9.1. Не рекомендую

- Оставлять Тип 2 на SQL + formula как production-решение.
- Пытаться "слегка подкрутить веса" и считать проблему решённой.
- Сразу прыгать в GNN / Transformer без данных и нормального логирования.
- Полностью полагаться на FAISS по среднему embedding корзины как на единственный retrieval-канал.

### 9.2. Рекомендую

Наиболее рациональный план:

1. Быстро улучшить текущий baseline retrieval внутри группы.
2. Построить гибридный multi-source retrieval для сценариев.
3. Собрать логи показов и действий.
4. Обучить отдельный CatBoost ranker для Типа 2.
5. Только потом решать, нужен ли basket encoder / sequential model.

Именно этот путь даёт лучший баланс:

- качество;
- скорость внедрения;
- стоимость;
- объяснимость;
- совместимость с текущей архитектурой `Go + Python + PostgreSQL`.

## 10. Что можно переиспользовать из текущего решения

Не всё нужно переписывать.

Можно сохранить:

- общий split на Go backend и Python ML service;
- `product_embeddings`;
- FAISS / ANN подход как основу одного из retrieval-каналов;
- CatBoost как технологию ранжирования;
- `scenario_feedback_stats`;
- `copurchase_stats`;
- feature engineering как основу, но не как финальную схему для Типа 2;
- модель комплементарности как важный источник признаков и retrieval.

Нужно переделать:

- retrieval для сценариев;
- постановку обучения ранкера;
- event logging;
- хранение сценариев;
- pipeline обновления индексов;
- метрики и валидацию для Type 2.

## 11. Метрики, которыми стоит мерить улучшение

### Offline

- Recall@K по группе сценария
- NDCG@K
- MRR@K
- coverage по товарам
- coverage по брендам
- group completion uplift
- доля zero-result ответов
- качество на cold-start SKU
- качество на смешанных корзинах

### Online

- CTR по карточкам группы
- add-to-cart rate
- attach rate по обязательным группам
- conversion to order
- uplift среднего количества товаров в заказе
- uplift GMV / margin
- доля завершённых сценариев

### Guardrails

- p95 latency
- разнообразие выдачи
- over-concentration по бренду
- out-of-stock recommendation rate

## 12. Вопросы для обсуждения с тимлидом

1. Нужна ли строгая привязка сценариев к ручной конфигурации, или сценарии в будущем должны стать частично динамическими?
2. Хотим ли мы оптимизировать рекомендации в первую очередь под CTR, add-to-cart, закрытие обязательных групп или GMV?
3. Есть ли доступ к order history, cart history и session events в достаточной детализации?
4. Можно ли писать полноценный exposure log для сценарных рекомендаций?
5. Какая допустимая latency на один запрос сценарных рекомендаций?
6. Можно ли использовать отдельный ANN-индекс, или предпочтительнее `pgvector` / PostgreSQL-only решение?
7. Насколько важна explainability в ответе сервиса?

---

## 13. Короткий вывод

Сценарные рекомендации нужно развивать не как "ещё одну формулу", а как отдельную recommender задачу:

- свой retrieval,
- свой ranker,
- свои данные обучения,
- свои метрики.

Самый сильный и реалистичный путь для этого проекта:

- hybrid retrieval,
- scenario-specific CatBoost ranker,
- полноценное логирование,
- поэтапный переход к basket/session models после накопления данных.
