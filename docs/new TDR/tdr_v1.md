# TDR: ML-система рекомендаций сопутствующих товаров
---

## 1. Executive Summary

### Бизнес-задача

Покупатель строительных материалов при выборе основного товара часто не знает, что ещё нужно докупить, забывает сопутствующие материалы или выбирает несовместимые. Система автоматически определяет контекст покупки и рекомендует недостающие товары, повышая средний чек и качество сервиса.

### Что строим

ML-сервис рекомендаций и Go-бэкенд для работы с данными магазина. Фронтенд и пользовательский интерфейс — вне скоупа: рекомендации потребляются внешними системами магазина через API.

### Ключевые технические решения

- Семантические эмбеддинги товаров (768 измерений) через локальную модель — без зависимости от внешних API
- Двухуровневое ранжирование: FAISS для быстрого поиска кандидатов + CatBoost для ML-ранжирования по 44 признакам
- Сценарный подход: предопределённые сценарии ремонта (5 типов) для контекстных рекомендаций
- Система фидбека с байесовским сглаживанием и непрерывным дообучением модели
- Дополнительная модель комплементарности категорий для cross-category рекомендаций

### Метрики качества (достигнуты на хакатонных данных)

| Метрика | Значение | Описание |
|---------|----------|----------|
| NDCG@10 | 0.70+ | Качество ранжирования топ-10 |
| AUC | 0.86+ | Способность отличать релевантные от нерелевантных |
| Inference | < 100ms | Полный цикл рекомендаций |
| FAISS поиск | ~1ms | Поиск 100 кандидатов в in-memory индексе |

                                           → сохраняет модель на диск (.cbm файл)
                                           → загружает в память

## 3. ML Pipeline

### 3.1 Обзор pipeline

[ДИАГРАММА: Блок-схема из 5 последовательных шагов. 1. "Определение сценария" (по category_id товара из запроса). 2. "Candidate Retrieval" (из групп сценария ИЛИ FAISS поиск — до 100 кандидатов). 3. "Feature Extraction" (44 признака на каждую пару товар-кандидат). 4. "Scoring" (CatBoost Ranker ИЛИ формульный fallback). 5. "Top-K отбор" (топ-20 с объяснениями).]

**Pipeline для рекомендаций на странице товара (`GET /recommendations/{product_id}`):**

1. **Загрузка товара** — получить данные товара по ID, включая category_id
2. **Определение сценария** — сопоставить category_id с одним из 5 сценариев ремонта
3. **Candidate Retrieval:**
   - Если сценарий найден: выбрать до 100 товаров из связанных групп сценария (по 50 из каждой группы)
   - Если сценарий не найден: FAISS nearest-neighbor поиск, k = min(500, всего товаров), взять топ-100
4. **Feature Extraction:** для каждой пары (основной товар, кандидат) извлечь 44 признака
5. **Scoring:**
   - При наличии обученной модели: CatBoost Ranker predict → нормализация в диапазон [0.5, 1.0]
   - Fallback: формульный скоринг на основе весовых коэффициентов
6. **Отбор топ-20** с добавлением rank и match_reasons

```python
# build_product_text() — точная реализация из кода
text = f"{name}. Категория: {category_path}. Производитель: {vendor}. {description[:500]}. Характеристики: {params_summary}"

```

#### Хранение

Таблица `product_embeddings`:
- `product_id` (INTEGER, PK) — ссылка на products
- `embedding` (FLOAT[]) — вектор 768 float значений
- `text_representation` (TEXT) — текст, на основе которого сгенерирован вектор

#### Загрузка в память при старте

При старте ML-сервиса все эмбеддинги загружаются в FAISS-индекс через `product_recommender.load_embeddings(session)`. Это происходит синхронно в `lifespan` хуке приложения — сервис не принимает запросы, пока индекс не готов.

### 3.3 Candidate Retrieval — FAISS

#### Конфигурация индекса

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| Тип индекса | `IndexFlatIP` | Inner Product на нормализованных векторах = косинусное сходство |
| Нормализация | `faiss.normalize_L2()` перед добавлением | Приводит к единичной норме для IP = cosine |
| Размерность | 768 | Соответствует размерности nomic-embed-text |
| Режим поиска | Точный (не приближённый) | При ~60k товаров достаточно быстро, ANN не нужен |
| k соседей | min(500, len(all_products)) | Потолок для последующего отбора 100 кандидатов |

#### Два пути candidate retrieval

**Путь A — Сценарный (приоритетный):**
- Активируется если category_id товара входит в один из 5 сценариев
- Для каждой группы сценария (кроме группы самого товара): выбрать до 50 товаров из категорий группы
- Итого: до 100 кандидатов из товарно-связанных категорий

**Путь B — Семантический (fallback):**
- FAISS поиск k = min(500, total) ближайших соседей
- Из результатов исключаются товары той же категории (penalty -0.15 к score)
- Берутся топ-100 по FAISS score

### 3.4 Feature Engineering — 44 признака

[ДИАГРАММА: Таблица или mind-map из 8 групп признаков с количеством в каждой группе.]

#### Группа 1: Семантические (6 признаков)

| Признак | Формула |
|---------|---------|
| `embedding_cosine_similarity` | dot(norm_a, norm_b) |
| `embedding_l2_distance` | L2 расстояние нормализованных векторов |
| `embedding_dot_product` | dot(norm_a, norm_b) без деления |
| `embedding_euclidean_distance` | Евклидово расстояние сырых векторов |
| `embedding_manhattan_distance` | Манхэттенское расстояние |
| `embedding_has_valid` | 1.0 если оба эмбеддинга присутствуют |

*Нормализация:* `vector / (norm(vector) + 1e-8)` для предотвращения деления на ноль.
*Fallback при отсутствии эмбеддингов:* cosine=0.5, l2=1.0, dot=0.0, euclidean=1.0, manhattan=1.0, has_valid=0.0.

#### Группа 2: Фидбек (8 признаков)

| Признак | Описание |
|---------|----------|
| `pair_feedback_positive` | Количество лайков для пары |
| `pair_feedback_negative` | Количество дизлайков для пары |
| `pair_feedback_total` | Сумма оценок |
| `pair_feedback_approval_rate` | (positive + 1) / (total + 2) — Laplace smoothing |
| `scenario_feedback_positive` | Лайки в контексте сценария |
| `scenario_feedback_negative` | Дизлайки в контексте сценария |
| `scenario_feedback_total` | Сумма сценарных оценок |
| `scenario_feedback_approval_rate` | (positive + 1) / (total + 2) — Laplace smoothing |

*Байесовское сглаживание (Laplace):* предотвращает проблему cold start. Товар с 1 лайком получает 67%, а не 100%.

#### Группа 3: Ценовые (7 признаков)

| Признак | Формула |
|---------|---------|
| `candidate_price` | Цена кандидата |
| `price_ratio` | candidate_price / max(main_price, 1) |
| `price_diff` | candidate_price - main_price |
| `price_diff_percent` | (price_diff / max(main_price, 1)) * 100 |
| `has_discount` | 1.0 если есть discount_price |
| `discount_percent` | (price - discount_price) / price * 100 |
| `discount_amount` | price - discount_price |

#### Группа 4: Категорийные (5 признаков)

| Признак | Формула |
|---------|---------|
| `same_category` | 1.0 если category_id совпадает |
| `same_root_category` | 1.0 если совпадает корневая категория |
| `category_distance` | 0.0 / 2.0 / 3.0 (same root / разные root) |
| `same_vendor` | 1.0 если vendor совпадает |
| `different_vendor` | 1.0 - same_vendor |

*Дерево категорий:* обход через рекурсивный CTE запрос к таблице categories.

#### Группа 5: Co-purchase (3 признака)

| Признак | Формула |
|---------|---------|
| `copurchase_count` | Количество совместных покупок |
| `copurchase_log` | log(1 + copurchase_count) |
| `copurchase_exists` | 1.0 если count > 0 |

#### Группа 6: Популярность товара (7 признаков)

| Признак | Формула |
|---------|---------|
| `has_image` | 1.0 если есть picture |
| `is_discounted` | 1.0 если есть discount_price |
| `price_bucket` | 0: ≤1000 руб, 1: ≤10000 руб, 2: >10000 руб |
| `name_length` | float(len(name)) |
| `view_count` | log(1 + view_count) |
| `cart_add_count` | log(1 + cart_add_count) |
| `order_count` | log(1 + order_count) |

#### Группа 7: Контекст корзины (3 признака)

| Признак | Описание |
|---------|----------|
| `cart_similarity_max` | Максимальное косинусное сходство с товарами в корзине |
| `cart_similarity_avg` | Среднее косинусное сходство с товарами в корзине |
| `cart_products_count` | Количество товаров в корзине |

*При отсутствии данных о корзине:* все три признака = 0.0.

#### Группа 8: Комплементарность категорий (5 признаков)

| Признак | Описание |
|---------|----------|
| `complementarity_score` | Скор модели комплементарности (LogisticRegression) |
| `category_semantic_similarity` | Косинусное сходство эмбеддингов категорий |
| `scenario_category_match` | 0.5 — одна группа (замены), 1.0 — разные группы (дополнения) |
| `copurchase_category_count` | log(1 + количество co-purchase на уровне категорий) |
| `categories_in_same_scenario` | Количество сценариев, где обе категории встречаются вместе |

### 3.5 Ранжирование — CatBoost Ranker

#### Архитектура модели

| Параметр | Значение |
|----------|----------|
| Алгоритм | CatBoostRanker (Learning-to-Rank) |
| Loss function | YetiRank |
| Eval metric | NDCG:top=10 |
| Custom metrics | NDCG:top=10, PrecisionAt:top=5 |
| Iterations | 500 (по умолчанию, диапазон 100–2000) |
| Learning rate | 0.05 (по умолчанию, диапазон 0.001–0.5) |
| Depth | 6 (по умолчанию, диапазон 3–10) |
| Random seed | 42 |
| use_best_model | True |

#### Схема обучения

[ДИАГРАММА: Схема формирования обучающей выборки. Слева: два источника позитивных примеров (pair_feedback_stats с positive_count≥5, и order_items с copurchase≥2). Справа: два источника негативных примеров (pair_feedback_stats с negative>positive, и hard negatives 3:1). Внизу: разбивка train/val 80/20 по group_id (main_product_id).]

**Источники обучающих данных:**

| Тип | Источник | Условие | Метка |
|-----|----------|---------|-------|
| Позитивные | `pair_feedback_stats` | positive_count ≥ 5 | y = 1 |
| Позитивные | `order_items` (co-purchase) | совместные покупки ≥ 2, лимит 10 000 пар | y = 1 |
| Негативные | `pair_feedback_stats` | negative_count > positive_count | y = 0 |
| Негативные | Hard negatives | случайные товары, ratio 3:1 к позитивным | y = 0 |

- Группировка: по `main_product_id` (query) — обязательное требование CatBoost Ranker
- Разбивка train/val: 80/20 по уникальным группам, а не по примерам
- Минимум: 100 обучающих примеров (иначе ошибка)

#### Нормализация выходных скоров

После predict модели скоры нормализуются в диапазон [0.5, 1.0]:
```
normalized = (raw_score - min_score) / score_range
final_score = 0.5 + normalized * 0.5
```
При `score_range == 0`: `final_score = 0.5` (все кандидаты одинаковы).

#### Формульный fallback (при отсутствии обученной модели)

```
score = 0.5 (база)
+ semantic_similarity * 0.3   (если есть эмбеддинги)
+ (pair_approval - 0.5) * 0.4 (если есть фидбек)
+ (scenario_approval - 0.5) * 0.2 (если есть сценарный фидбек)
+ discount_percent * 0.1      (если есть скидка)
```
Итоговый score обрезается в диапазон [0, 1].

#### Персистентность модели

- Формат: `.cbm` файлы (CatBoost native format)
- Именование: `catboost_ranker_{timestamp}.cbm` (timestamp: `%Y%m%d_%H%M%S`)
- Метаданные: `catboost_ranker_{timestamp}_metadata.json`
- При старте: автоматически загружается последняя модель по дате изменения файла

### 3.6 Комплементарность категорий

Отдельная ML-модель для определения, являются ли две категории товаров дополнением друг к другу (штукатурка + шпатели) в отличие от замены (штукатурка KNAUF + штукатурка Ceresit).

#### Архитектура

| Параметр | Значение |
|----------|----------|
| Алгоритм | LogisticRegression (scikit-learn) |
| C (регуляризация) | 1.0 |
| class_weight | balanced (для работы с дисбалансом классов) |
| max_iter | 1000 |
| random_state | 42 |

#### Как вычисляются эмбеддинги категорий

Эмбеддинг категории = среднее арифметическое эмбеддингов всех товаров в этой категории:
```sql
SELECT c.id, ARRAY_AGG(pe.embedding)
FROM categories c
JOIN products p ON p.category_id = c.id
JOIN product_embeddings pe ON pe.product_id = p.id
WHERE pe.embedding IS NOT NULL
GROUP BY c.id
```
Среднее: `np.mean(embeddings_array, axis=0)`, тип `np.float32`.

#### Feature vector для пары категорий (4×768 + 1 = 3073 признака)

```python
emb1_norm = emb1 / (norm(emb1) + 1e-8)
emb2_norm = emb2 / (norm(emb2) + 1e-8)
diff = emb1_norm - emb2_norm
product = emb1_norm * emb2_norm
cosine = dot(emb1_norm, emb2_norm)
features = concat([emb1_norm, emb2_norm, diff, product, [cosine]])
```

#### Обучающие данные

- Источник: файл `recommendations/data/complementary_categories.csv`
- Формат: `category_id_1, category_id_2, is_complementary, relation_type`
- Разбивка: train/test 80/20, stratify=y
- Нормализация: StandardScaler

#### Предвычисленная матрица

После обучения скоры для всех пар категорий предвычисляются и хранятся в памяти в виде словаря `{(cat1, cat2): score}`. Это позволяет мгновенно получить скор во время inference без повторного вычисления.

#### Типы отношений

| Тип | Условие |
|-----|---------|
| `same_group` | Обе категории в одной группе сценария |
| `tool` | Ключевые слова: "инструмент", "валик", "шпател" |
| `material` | Ключевые слова: "материал", "смес" |
| `related` | Разные группы одного сценария |
| `unrelated` | Нет пересечений в сценариях |

#### Персистентность

4 pickle-файла в директории `models/`:
- `complementarity_model.pkl` — LogisticRegression
- `complementarity_scaler.pkl` — StandardScaler
- `complementarity_matrix.pkl` — предвычисленные скоры

## 4. Данные и обучение

### 4.1 Схема ML-таблиц

[ДИАГРАММА: ER-диаграмма ML-таблиц. products как центральная сущность. Связи: product_embeddings (1:1), product_stats (1:1), copurchase_stats (M:N через product_id_1/2), product_pair_feedback (M:N через main+recommended), pair_feedback_stats (агрегат pair_feedback). Отдельно: scenario_feedback и scenario_feedback_stats (без FK на products — только product_id). recommendation_events (M:N с products через main+recommended).]

**ML-таблицы и их назначение:**

| Таблица | Назначение | Ключевые поля |
|---------|------------|---------------|
| `product_embeddings` | Векторные представления товаров | product_id (PK), embedding (FLOAT[]) |
| `product_stats` | Поведенческая статистика | product_id (PK), view_count, cart_add_count, order_count |
| `copurchase_stats` | Совместные покупки | product_id_1, product_id_2 (PK), copurchase_count |
| `product_pair_feedback` | Сырой фидбек на пары товаров | id, main_product_id, recommended_product_id, feedback_type |

### 4.2 Источники сигналов для обучения

**Co-purchase из заказов:**
- Источник: таблица `order_items` (пары товаров из одного заказа)
- Алгоритм: для каждого заказа с 2+ товарами генерируются все пары комбинаций
- Пары нормализованы: key = (min(id1, id2), max(id1, id2))
- Обновление: пересчёт через TRUNCATE + полную перезагрузку (скрипт `update_copurchase.py`)
- Минимальный порог для обучения: copurchase_count ≥ 2

**Явный фидбек пользователей:**
- Пара товаров: `product_pair_feedback` → агрегируется в `pair_feedback_stats`
- Сценарный: `scenario_feedback` → агрегируется в `scenario_feedback_stats`
- Хранение: UPSERT с `ON CONFLICT DO UPDATE SET count = count + 1`

**Поведенческие события:**
- Таблица `recommendation_events`: impression, click, add_to_cart
- Типы: impression (показ), click (клик), add_to_cart (добавление в корзину)
- Требуют user_id или session_id

### 4.3 Cold Start и синтетический фидбек

**Проблема:** при запуске без реальных данных нет обучающей выборки для CatBoost.

**Решение:** скрипт `generate_synthetic_feedback.py` генерирует начальный фидбек.

**Параметры генерации по умолчанию:**
- Всего пар: 500 (настраивается через параметр `count`)
- Доля позитивных: 70% → 350 пар
- Доля негативных: 30% → 150 пар

**Алгоритм позитивных пар:**
1. Загрузить до 5000 товаров с эмбеддингами (доступных)
2. Группировать по category_id
3. Для пар внутри одной категории вычислить cosine similarity
4. Если similarity > 0.3 → позитивная пара
5. positive_count = random(3, 15)

**Алгоритм негативных пар:**
1. Случайно выбрать два товара из разных категорий
2. Проверить на дубликаты
3. negative_count = random(2, 8)

**Ограничение:** синтетический фидбек создаёт смещение в данных — модель, обученная только на нём, будет переоценивать внутрикатегорийное сходство. Рекомендуется дообучение по мере накопления реального фидбека.

### 4.4 Сценарии ремонта

Предопределённые наборы категорий товаров для типичных ремонтных работ. Используются для двух задач: определение контекста товара и формирование групп рекомендаций.

| ID | Название | Групп | Обязательных |
|----|----------|-------|--------------|
| `floor` | Монтаж наливного пола | 8 | 5 |
| `partitions` | Монтаж перегородок | 7 | 7 |
| `walls` | Выравнивание стен | 8 | 7 |
| `tiling` | Укладка плитки | 10 | 7 |
| `electrical` | Электромонтаж | 8 | 7 |

**Определение сценария для товара:** сопоставление `category_id` товара с `category_ids` групп сценариев (прямое вхождение).

**Определение сценария для корзины:** для каждого сценария считается прогресс — количество групп, покрытых товарами корзины. Возвращается сценарий с наибольшим прогрессом.

**Структура сценария (пример: `walls` — Выравнивание стен):**

| Группа | Category IDs | Обязательна |
|--------|-------------|-------------|
| Штукатурка гипсовая | [25178] | Да |
| Грунтовки | [25380] | Да |
| Шпатлёвки | [25179, 30462] | Да |
| Ёмкости строительные | [25252] | Да |

### 4.5 Процесс переобучения модели

**Триггер:** `POST /ml/train` (ручной или по расписанию)

**Параметры запроса:**

| Параметр | По умолчанию | Диапазон |
|----------|-------------|---------|
| iterations | 500 | 100–2000 |
| learning_rate | 0.05 | 0.001–0.5 |
| depth | 6 | 3–10 |
| min_feedback_count | 5 | 1–20 |

**Время обучения:** 1–5 минут в зависимости от объёма данных.

**Рекомендуемые условия для переобучения:**
- Накопилось 100+ новых оценок фидбека
- Значительный рост заказов (новые co-purchase данные)
- Регулярно раз в неделю при активном использовании

### 5.3 Последовательность запуска сервиса

При старте Python ML-сервиса в порядке очереди:
1. `init_db()` — инициализация SQLAlchemy, проверка подключения к PostgreSQL
2. `scenarios_service.initialize(session)` — загрузка конфигурации сценариев
3. `product_recommender.load_embeddings(session)` — загрузка всех эмбеддингов и построение FAISS-индекса
4. `category_embeddings_service.compute_embeddings(session)` — вычисление эмбеддингов категорий
5. `complementarity_model.get_model_info()` — проверка и загрузка модели комплементарности (если обучена)

Сервис недоступен для запросов до завершения всех шагов. Самый долгий шаг — загрузка FAISS (зависит от количества товаров).

## 6. Производительность и надёжность

### 6.1 Latency по шагам pipeline

| Операция | Время | Примечание |
|----------|-------|------------|
| FAISS search (k=100) | ~1ms | In-memory, IndexFlatIP |
| Feature extraction (44 признака, 100 кандидатов) | ~10ms | Batch SQL запросы |
| CatBoost predict (100 кандидатов) | ~50ms | CPU inference |
| Полный цикл рекомендаций | < 100ms | Без сетевых задержек |
| Генерация одного эмбеддинга (Ollama) | 50–200ms | Зависит от длины текста |

### 6.2 Потребление памяти

- FAISS индекс: ~60k товаров × 768 float × 4 байта ≈ **185 MB**
- Матрица комплементарности: dict в памяти, зависит от числа категорий
- CatBoost модель: несколько MB (500 деревьев)

### 6.3 Поведение при деградации

| Ситуация | Поведение |
|----------|-----------|
| CatBoost модель не обучена | Формульный скоринг (fallback) |
| Эмбеддинг товара отсутствует | Предустановленные значения: cosine=0.5, l2=1.0 и т.д. |
| Нет фидбека для пары | pair_approval_rate = (0+1)/(0+2) = 0.5 (нейтрально) |
| FAISS: товар без эмбеддинга | Сценарный retrieval или пустой результат |
| Complementarity model не загружена | Признаки комплементарности = 0 |

### 6.4 Зависимости

**Обязательные:**
- PostgreSQL 16 — все данные
- Python ML-сервис — FAISS, CatBoost модели

**При первоначальной генерации эмбеддингов:**
- Ollama с моделью nomic-embed-text (274 MB) — только для генерации эмбеддингов новых товаров

**Ключевые Python-зависимости:**

| Пакет | Версия | Назначение |

| numpy | 1.26.3 | Численные вычисления |
| faiss-cpu | 1.7.4 | Векторный поиск |
