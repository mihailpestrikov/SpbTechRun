# Целевой вариант реализации сценарных рекомендаций

## 1. Что делаем
Систему сценарных рекомендаций для магазина.
Система должна определять сценарий по корзине или принимать его явно, понимать закрытые и незакрытые группы, рекомендовать недостающие товары по каждой группе и ранжировать их по вероятности выбора и полезности для завершения сценария.

## 2. Целевой pipeline
1. Пользователь приходит с корзиной или с явно выбранным сценарием.
2. Система определяет сценарий и прогресс по нему.
3. Для каждой незакрытой группы собирается широкий релевантный пул кандидатов.
4. Кандидаты ранжируются отдельной ML-моделью для задачи `(корзина, сценарий, группа) -> товар`.
5. Пользователь получает лучшие товары по каждой группе.
6. Все показы и действия логируются и используются в обучении.

## 3. Архитектура
Система состоит из двух сервисов: `Go backend / Data API` и `Python ML service`.
Go backend отвечает за синхронизацию данных магазина, хранение локальной копии данных контура рекомендаций, сбор событий и фидбека и отдачу API.
Python ML service отвечает за подбор кандидатов, ранжирование, работу с эмбеддингами, обучение.
Нужен отдельный постоянно обновляемый слой данных, где хранятся товары, категории, цены, наличие, акции, базовые атрибуты, эмбеддинги, co-purchase, характеристики товаров, фидбэк по рекомендациям, сценарии и группы сценариев.

## 4. Сценарии как данные
Сценарии должны храниться в БД, а не в коде.
Для сценария нужно хранить: `scenario_id`, название, описание, статус, порядок.
Для группы: `group_id`, название, список `category_id`, обязательность, порядок, правила показа альтернатив.
Дополнительно нужно поддержать жёсткие правила совместимости и несовместимости для отдельных групп и категорий, а также версионирование сценариев, чтобы понимать по какой версии сценария были выданы рекомендации и какие результаты она показала.

## 5. Вход и определение сценария
На вход сценарного inference должны поступать `scenario_id` или `cart_product_ids`, `session_id` / `user_id`, текущая корзина, канал запроса и timestamp.
Если сценарий не передан явно, система должна:
- загрузить категории товаров корзины;
- оценить соответствие корзины каждому сценарию;
- выбрать лучший сценарий;
- посчитать уверенность;
- не навязывать сценарий при низкой уверенности.

После выбора сценария нужно разложить корзину по группам, определить закрытые и незакрытые группы и посчитать прогресс по обязательным группам. Прогресс должен использоваться и в UI, и как ML-сигнал.

## 6. Retrieval

### 6.1 Каналы подбора кандидатов
Для каждой незакрытой группы нужен гибридный подбор кандидатов из нескольких каналов:
- `Group popularity`: товары нужных категорий, доступные к продаже, отсортированные по популярности, заказам, добавлениям в корзину и качеству карточки.
- `Basket-to-item embedding retrieval`: представление корзины как контекст, поиск товаров, близких к этому контексту, затем фильтрация по нужной группе.
- `Co-purchase retrieval`: товары, которые часто покупают вместе с товарами корзины.
- `Complementarity retrieval`: товары из функционально совместимых категорий.
- `Scenario prior`: что чаще выбирают, покупают и чем чаще закрывают группу.

Подбор и фильтрация кандидатов должны учитывать доступность товара в конкретном магазине, регионе или канале продаж, если это важно для продукта.

### 6.2 Слияние кандидатов из разных каналов
Каждый канал генерирует свой набор кандидатов. Итоговый пул строится как объединение с дедупликацией. Для каждого кандидата сохраняются его источники и ранг в каждом канале — эти данные становятся признаками для ранкера.

Стандартный индустриальный подход (Alibaba, Pinterest, Airbnb): простое объединение кандидатов из всех каналов + полный re-ranking единой моделью. Модель сама учится взвешивать сигналы из разных каналов через retrieval-признаки.

До появления ML-ранкера для слияния используется Reciprocal Rank Fusion (RRF): `score(item) = sum(1 / (k + rank_in_channel))`, k=60. Это проверенный метод, не требующий нормализации скоров между каналами и работающий из коробки как baseline.

## 7. Ranking

### 7.1 Общий подход
Сценарное ранжирование должно быть отдельной моделью. Это не та же задача, что рекомендации на карточке товара.

Целевой вариант — отдельный CatBoostRanker для сценарных рекомендаций, learning-to-rank с группировкой по `(scenario_id, group_name, cart_state)`.

### 7.2 Как корзина становится входом для модели
CatBoost работает с табличными признаками. Корзина не подаётся как вектор — из неё извлекаются признаки взаимодействия с каждым кандидатом. Основные группы признаков сценарного ранкера:

**Basket-candidate (взаимодействие кандидата с корзиной):**
- косинусное сходство кандидата со средним эмбеддингом корзины и с ближайшим товаром корзины
- максимум и сумма co-purchase count кандидата с товарами корзины
- совпадение бренда с товарами корзины
- соотношение цены кандидата с медианой цен корзины

**Retrieval-source (из какого канала пришёл кандидат):**
- бинарные флаги: из popularity / co-purchase / embedding / complementarity
- ранг кандидата в каждом канале

**Candidate (свойства самого кандидата):**
- цена, скидка, популярность, наличие
- scenario_feedback, complementarity_score

Итого порядка 25–30 признаков. 

### 7.3 Жёсткие правила
Для части категорий поверх ML-ранжирования должен существовать слой жёстких правил, который не позволяет показывать несовместимые или запрещённые комбинации товаров. Возможно редактирование правил через админ-панель.

## 8. Альтернативы
Альтернативы должны быть частью общего сценарного режима.

Система должна уметь показывать замены внутри группы, альтернативы по цене и бренду, а также аналоги даже если сценарий уже почти закрыт.

Альтернативы должны ранжироваться тем же ML-контуром или близким к нему способом.

Отдельный режим дополнительных товаров можно рассматривать как потенциальное развитие сценарного режима, но не как замену основной задачи подбора.

## 9. Количество и достаточность
Система не должна ограничиваться только логикой "группа закрыта / не закрыта".
Для части товарных групп нужно поддержать подсказки по достаточности: помогает ли уже выбранное количество закрыть потребность пользователя.

В первой версии это могут быть ручные подсказки: для каждой группы сценария можно задать `hint_text` — текст вроде "Расход штукатурки: ~8 кг на 1 м2 при толщине слоя 10 мм". Подсказки хранятся как атрибут группы сценария и задаются при редактировании.

## 10. Какие данные нужно собирать
Нужно собирать: показ рекомендации, список показанных кандидатов, позицию кандидата, контекст сценария, контекст группы, снимок корзины, клик, add-to-cart, покупку, явный positive / negative feedback.

Нужно уметь связать:
- какой набор рекомендаций был показан;
- какой товар пользователь выбрал;
- что в итоге купил.

Без этого нельзя качественно обучать ranking-модель.

Критически важно логировать состояние корзины на момент каждого показа рекомендации. Без снимка корзины невозможно восстановить контекст запроса для обучения ранкера, и собранные данные теряют ценность.

Объясняемость должна быть частью продукта: системе нужно уметь объяснять пользователю, почему товар попал в конкретную группу рекомендаций.

## 11. Обучение

### 11.1 Структура обучающей выборки
Каждый обучающий пример описывает ситуацию: "при таком состоянии корзины, в таком сценарии, для такой группы — насколько хорош этот кандидат".

- **Query:** `(session_id, scenario_id, group_name, cart_state)` — группировка для обучения.
- **Кандидат:** товар, для которого считаются признаки.
- **Признаки:** 25–30 из раздела 7.2.
- **Метка релевантности:** 3 = покупка, 2 = добавление в корзину, 1 = клик, 0 = показан, но проигнорирован.

### 11.2 Позитивные и негативные примеры
Позитивные: товары, которые пользователь выбрал из показанных (click / add_to_cart / purchase).
Негативные:
- показанные, но не кликнутые (слабые негативы);
- случайные товары из той же группы, не попавшие в показ (сильные негативы);
- соотношение ~3:1 негативы к позитивам.

### 11.3 Position bias correction
Данные из логов показов содержат позиционное смещение: товары на первых позициях кликают чаще просто потому что их видят. Без коррекции модель будет закреплять текущий порядок вместо того чтобы его улучшать. Подход: добавить позицию показа как признак при обучении, зафиксировать её в 1 при inference. Альтернатива — взвешивание примеров обратной вероятностью показа.

### 11.4 Источники сигналов
Выбор товара из показанных рекомендаций, add-to-cart после показа, покупка после показа, явный фидбэк, co-purchase как дополнительный источник.

Переобучение сценарного ранкера должно быть отделено от товарного ранкера.

## 12. Cold start и поэтапный запуск

Сценарный ранкер нельзя обучить без данных о показах и реакциях пользователей. Поэтому запуск должен быть поэтапно — система сразу работает, а ML-модель подключается когда для неё появляются данные.

### Фаза 0 — до запуска
Формульный ранкер на основе RRF (Reciprocal Rank Fusion) по каналам retrieval. Каждый канал генерирует кандидатов, скоры сливаются через RRF. Параллельно подключается история заказов и co-purchase из продовых баз.

### Фаза 1 — запуск 
RRF-ранкер в проде. Логируются все показы, позиции, клики, add-to-cart, покупки, снимки корзины. Можно дополнительно сгенерировать синтетические обучающие примеры из co-purchase.

### Фаза 2 — первая ML-модель
Обучение CatBoost на собранных логах. A/B тест ML vs RRF.

### Фаза 3 — итеративное улучшение
Регулярное переобучение на накопленных данных, расширение признаков.

## 13. Что нужно сделать в backend
Backend должен:
- поднять локальную копию каталога;
- синхронизировать каталог, цены, наличие и акции;
- собирать историю заказов;
- собирать фидбэк по рекомендациям;
- передавать в ML-сервис контекст корзины и сценария;
- хранить и отдавать конфигурацию сценариев;
- поддерживать API для inference, фидбэка и логирования.

## 14. Что нужно сделать в ML-сервисе
ML-сервис должен:
- построить гибридный retrieval с несколькими каналами;
- реализовать RRF-слияние как baseline;
- реализовать отдельный ранкер для сценариев;
- подключить комплементарность категорий в сценарный пайплайн;
- учитывать контекст корзины как главный сигнал;
- корректно обрабатывать смешанные корзины;
- поддерживать обновление эмбеддингов и индексов;
- поддерживать fallback-режимы на каждом этапе.

## 15. Итоговый целевой вариант
Целевой вариант системы выглядит так:
- сценарии хранятся как управляемые данные;
- сценарии версионируются и анализируются как продуктовая сущность;
- контур рекомендаций имеет свою локальную витрину данных;
- сценарий определяется по корзине с оценкой уверенности;
- retrieval строится из нескольких источников, кандидаты сливаются и переранжируются;
- ranking делается отдельной ML-моделью для сценариев, обученной на реальном поведении;
- до появления ML-модели работает RRF-baseline, который уже даёт качество выше формульного;
- поверх ML-логики действуют жёсткие правила совместимости там, где это требуется;
- рекомендации учитывают магазин, регион или канал продаж, если это важно для доступности ассортимента;
- система умеет не только закрывать группы, но и подсказывать достаточность количества для части товарных категорий;
- все показы и действия пользователя логируются вместе со снимком корзины;
- обучение на логах включает коррекцию по позиционному смещению;
- explainability встроена в продукт и помогает понимать, почему товар рекомендован;
- модель регулярно переобучается на реальном поведении;
- backend и ML-сервис работают как единая система рекомендаций.
